## คำตอบสำหรับเจ้าของโครงการ

ไม่ต้องเดารูปแบบและอายุคลิปด้วยตัวเองทั้งหมด การตรวจมีสามส่วน:

1. ยืนยัน Short/Long จากต้นทางหรือผู้ตรวจ พร้อมหลักฐานว่าใครยืนยันและยืนยันชุดไหน ไม่กำหนดจากความยาวหรือ URL `watch` เพียงอย่างเดียว
2. ดึงวันที่เผยแพร่จาก API แล้วคำนวณอายุ ช่วงวางแผนใช้เวลาที่ตรวจ Metadata ได้ แต่ตอนฝึกจริงต้องใช้ `observed_at - published_at` ของ Observation สถิติจริง ไม่ใช่อายุของคลิปผู้ใช้ที่ยังไม่เผยแพร่
3. ตรวจว่าชุด Fit เดิมมีหมวด/Format/ช่วงอายุ/Metric ตรงกันเพียงพอหรือไม่ อย่างน้อย 20 คลิป/5 ช่อง/Label ทั้งสองระดับต่อบริบทตาม Protocol ปัจจุบัน จำนวนรวมทุกหมวดใช้แทนไม่ได้

คำยืนยันผู้ใช้สำหรับ **67 คลิปใหม่เท่านั้น**:

- รูปแบบ: “เป็นคลิปปกติทั้งหมด ไม่ใช่ Shorts” บันทึกในรายงานเป็น `long_form` โดยมีที่มา `owner_statement` ไม่อ้างว่า Agent เปิดดูวิดีโอทั้งหมดเอง
- วิธีเลือก: “ใช้หลายวิธีปนกัน/จำเกณฑ์ไม่ได้” จึงคง Sampling frame เป็น `unconfirmed` ไม่เปลี่ยนเป็น General หรือ High-response เอง
- คำตอบนี้ไม่ยืนยันความครบของ Transcript สิทธิ์ฝึก และรูปแบบของข้อมูลเดิมโดยอัตโนมัติ
- อัปเดตคำตอบเจ้าของวันที่ 12 ต.ค. 2026 สำหรับชุด NotebookLM เดิม: **“ชุดเดิมมี Shorts ปนด้วย”** เป็นคำยืนยันระดับชุด ไม่ใช่รายชื่อ Video ID จึงยังไม่ทราบว่ามี Shorts ในผู้สมัคร Train เต็มคลิป 172 รายการกี่รายการ ห้ามนำคำยืนยันคลิปปกติของชุดใหม่ไปใช้กับชุดเดิม
- ยังไม่แก้ Format ใน DB หรือแก้รายงาน Snapshot เก่าย้อนหลัง ต้องตรวจและบันทึกหลักฐานรายคลิปก่อนนับความเพียงพอใหม่ แยก Shorts/คลิปปกติโดยรักษา Split เดิม

## ขั้นตอนถัดไปที่ไม่ทำให้เก็บซ้ำโดยไม่จำเป็น

1. ชุดเดิมยืนยันแล้วว่าเป็นชุดผสม จึงต้องระบุ Short/Long **ราย Video ID** พร้อมหลักฐาน โดยเริ่มจากผู้สมัคร Train 172 รายการเพื่อทราบว่ามีคลิปปกติที่ใช้เทียบชุดใหม่เหลือเท่าไร รายการที่ยังไม่แน่ใจให้คง Unknown ไม่เดาจาก Duration หรือย้าย Split เดิม
2. ตรวจไฟล์ที่สงสัยว่าไม่เต็ม ขอข้อความตามเสียงจริงตั้งแต่ต้นจนจบ ไม่สรุป ไม่แปล และไม่ให้เติมคำพูดที่ไม่มีในคลิป โดยเฉพาะ Camera และ Phone; แก้ missing-caption ของ Laptop
3. แยกรายการซ้ำ/ทับช่องก่อน วางบทบาทตาม Identity เดิม ห้าม Approve All เพื่อให้ครบจำนวน
4. ทบทวนวิธีเลือกเป็นรายรายการหากมีหลักฐานค้นคืนได้ หากไม่สามารถยืนยันกรอบเก็บได้ คงเป็นข้อมูลวิจัย/ผู้สมัครชุดพัฒนา ไม่ติดป้าย General population เอง และไม่ใช้รับรอง Probability ของคลิปทั่วไป
5. หลังชุดเดิมและชุดใหม่ผ่านการตรวจ จึงวางกรอบเก็บ/ช่อง/บทบาทก่อนเก็บเพิ่ม ไม่สั่งหาใหม่อีก 60 แบบเดิม รายการที่เคยเสนอ 60 เป็นเป้าจำนวนที่ต้องใช้ประเมินได้จริง ไม่ใช่ทุกคลิปรีวิวที่เก็บครบจำนวนแล้วนับผ่าน
6. เมื่อตรวจสิทธิ์และขออนุมัติการบันทึก Metadata แล้วจึง Import แบบ pending review และใช้ workflow เดิม สถิติของชุด Outcome ให้ collector เดิมเก็บหลังมี Manifest/สิทธิ์พร้อม ไม่ใช้การตรวจ Metadata ครั้งนี้แทนสถิติ

## สถานะและข้อจำกัด

- Software audit: ผ่าน Tests และอ่าน DB จริงโดยมี write guard
- Format ของชุดใหม่: เจ้าของยืนยัน ไม่ใช่การตรวจวิดีโอโดย Agent

- Outcome Holdout ที่รับรองจาก 67 รายการนี้: **0 ในขณะนี้** ไม่ได้แปลว่าทุกรายการเสีย แต่ห้ามนับล่วงหน้า
