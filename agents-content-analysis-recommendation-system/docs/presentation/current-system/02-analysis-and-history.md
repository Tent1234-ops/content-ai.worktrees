# 2. วิเคราะห์คลิป ผลวิเคราะห์ และประวัติ

[กลับสารบัญ](README.md)

## หน้า “วิเคราะห์คลิปของฉัน”

**หน้าที่:** รับวิดีโอของผู้ใช้ ไม่ได้รับ URL YouTube เพื่อให้ผู้ใช้ต้องเผยแพร่ก่อน ระบบวิเคราะห์เสียงพูดเป็นหลัก ยังไม่ได้เข้าใจทุกภาพ การตัดต่อ หรือภาษากายของวิดีโอ

ค่าปัจจุบัน: วิดีโอไม่เกิน **300 วินาที**, Whisper **small**, ช่วงเปิดคลิป **60 วินาที** ค่านี้อ่านจาก Database ไม่ใช่ Frontend เดาเอง

| สิ่งบนหน้า | ความหมาย |
|---|---|
| เลือกไฟล์ / เปลี่ยนไฟล์ | เลือกวิดีโอที่จะส่ง ไม่ใช่ส่งเข้า Dataset ฝึกอัตโนมัติ |
| ข้อจำกัดความยาว | เงื่อนไขไฟล์ผู้ใช้ Backend ตรวจซ้ำด้วย metadata ของไฟล์จริง |
| เริ่มวิเคราะห์ | ส่งไฟล์ เก็บ settings ณ ตอนนั้น แล้วรับรหัสงานกลับมา |
| กำลังเตรียมเสียง | แยกเสียงจากวิดีโอ |
| กำลังถอดเสียง | Whisper แปลงเสียงเป็นข้อความทั้งคลิปพร้อมช่วงเวลา |
| กำลังจำแนก / เปรียบเทียบ | เรียกโมเดลและกลไกหลักฐาน ไม่ใช่กำลังค้นคำในอินเทอร์เน็ตทุกคำ |
| กำลังบันทึก | เขียนผลลง DB รอสำเร็จก่อนแจ้งว่าบันทึกแล้ว |
| Error | งานไม่สำเร็จ ต้องดูสาเหตุ ไม่ใช้ชื่อไฟล์ปลอมเป็น Transcript เพื่อแนะนำต่อ |

### ลำดับจริงจาก Frontend ถึง Database

```text
1. Frontend GET /analyze/settings -> รับข้อจำกัดจริง
2. POST /analyze/save + ไฟล์ -> ตรวจ Login/ความยาว/ไฟล์
3. เก็บไฟล์ videos/<รหัสไม่ซ้ำ>_<ชื่อเดิม> และคัดลอก settings + Model ID
4. คืน job_id -> Browser GET /jobs/<id> เพื่อตรวจสถานะ
5. Worker แยกเสียง -> faster-whisper -> Raw Transcript + segments
6. Normalize เฉพาะศัพท์ที่กำหนดชัด -> Cleaned Transcript
7. Active classifier ทายจากข้อความ -> ตรวจรับหมวด/Unknown
8. สกัดคำทั้งคลิปและช่วงเปิด -> รวมคำพ้องเป็นประเด็นมาตรฐาน
9. ถ้ารับหมวดได้: คัดคลิปอ้างอิง -> เทียบประเด็น -> สร้างคำแนะนำ/หลักฐาน
10. ถ้ารับหมวดไม่ได้: งดคำแนะนำเฉพาะหมวด แต่ยังเก็บข้อความและเหตุผลได้
11. บันทึกผล -> คืน content_id -> เปิดหน้าผลวิเคราะห์
```

ไฟล์เริ่มทางเดินคือ [analyze.py](../../../app/routes/analyze.py), เรียก [pipeline/core.py](../../../app/services/pipeline/core.py), [speech_to_text.py](../../../models/speech_to_text.py), [classification.py](../../../app/services/classification.py), [recommendation.py](../../../app/services/recommendation.py) แล้วบันทึกผ่าน [persistence.py](../../../app/services/persistence.py)

### Raw / Cleaned / Timestamp ต่างกันอย่างไร

- Raw คือข้อความที่ Whisper คืนมา เก็บไว้ย้อนตรวจได้ ไม่ใช่การรับรองว่าเสียงถอดถูกทุกคำ
- Cleaned คือจัดช่องว่าง/รูปแบบและ normalize เฉพาะศัพท์ที่มี mapping ในโค้ด ไม่ใช่แก้สะกดทั้งย่อหน้าให้ฟังดูดีเอง
- segments คือข้อความพร้อมเวลาเริ่ม/จบที่เครื่องถอดเสียงให้มา เวลาไม่ใช่การจับด้วยมนุษย์และอาจคลาดเคลื่อนได้
- Hook ใช้ช่วงเวลาจริงที่ตั้งไว้ ไม่ใช้ “60 คำแรก” แทน 60 วินาที
- Transcript ที่ Admin นำเข้าแบบไม่มีเวลา ยังใช้ตรวจว่าพูดเรื่องใดได้ แต่ห้ามสร้าง Timestamp หรือยืนยันว่าอยู่ใน 60 วินาทีแรกขึ้นมาเอง

## หน้า “ผลวิเคราะห์คลิป”

โครงหน้าเรียง **พบอะไร -> ควรเพิ่มอะไร -> เพราะอะไร** คำดิบและหลักฐานอยู่ในส่วนขยาย ไม่ต้องอ่านคะแนนภายในทั้งหมดก่อนเข้าใจข้อเสนอ

### 1. พบอะไรในคลิป

| หัวข้อ/ข้อความ | อ่านให้ถูก |
|---|---|
| หมวดหมู่ของคลิป | ผลที่ผ่านการตรวจรับแล้ว: Phone / Camera / Laptop / Unknown |
| ผลทายก่อนตรวจรับ | คำตอบดิบของโมเดลเพื่ออธิบายการตัดสิน อาจเป็น Phone แต่สุดท้ายระบบยังไม่รับ |
| Confidence / ความมั่นใจ | คะแนนของตัวจำแนก ไม่ใช่คุณภาพคลิป ไม่ใช่ความแม่นของคำแนะนำ ไม่ใช่โอกาสดัง |
| คำสำคัญที่พบทั้งคลิป | คำ/วลีที่มีหลักฐานในข้อความผู้ใช้ ไม่ใช่คำที่อยากให้เพิ่ม |
| คำสำคัญที่พบในช่วงเปิดคลิป | สิ่งที่ตรวจพบในช่วง Hook ตามเวลา |
| หัวข้อหลักที่ใช้เปรียบเทียบ | แนวคิดมาตรฐานที่รวมคำพ้อง เช่น แบต/แบตเตอรี่ -> battery life เพื่อไม่แนะนำเรื่องเดิมซ้ำเพียงเพราะใช้คนละคำ |
| ข้อความต้นฉบับ | Raw Transcript จาก ASR |
| ข้อความหลังปรับศัพท์ | Cleaned Transcript ที่ใช้ประมวลผล |

**วิธีจับคำ:** `nlp.py::tokenize_text()` ใช้ PyThaiNLP ตัดคำไทย แล้ว `filter_tokens()` ตัดคำทั่วไปและเลขล้วน `extract_keyword_candidates()` นับคำ/วลีด้วย `Counter` และกฎให้ค่าน้ำหนักวลี จากนั้นเรียงและตัดซ้ำ

ตัวอย่างตรรกะที่ใช้จริง: คำเดี่ยวได้คะแนนเริ่มจากจำนวนครั้ง; วลี 2 คำที่พบซ้ำอย่างน้อย 2 ครั้งใช้ `จำนวนครั้ง x 1.8 + 0.3`; วลี 3 คำใช้ `จำนวนครั้ง x 2.2 + 0.4` และศัพท์เฉพาะมีน้ำหนักเพิ่มเติม คะแนนเหล่านี้เป็นค่าจัดลำดับคำ **ไม่ใช่ค่าความน่าจะเป็น**

สิ่งนี้ต่างจาก Feature ของตัวจำแนก: ตัวจำแนกอ่าน Transcript ผ่านตัวแปลง TF-IDF/embedding ของโมเดลนั้นเอง ไม่ได้เอา Keyword ที่แสดงเพียง 10 คำไปทายหมวดทั้งหมด

### 2. ควรเพิ่มอะไร

แต่ละคำแนะนำมี “สิ่งที่พบ / ข้อเสนอ / เงื่อนไข / วิธีเพิ่มเนื้อหา / ประโยคตัวอย่าง / เหตุผล” เช่น หากมีหลักฐานเรื่องแบตแต่ยังไม่พบเรื่องเวลาชาร์จ อาจเสนอให้ทดสอบช่วงชาร์จและรายงานสภาพการทดสอบ ไม่ใช่สั่งพูดคำว่า “ชาร์จ” ซ้ำ ๆ

ระบบใช้แม่แบบภาษาไทยใน [recommendation_templates.json](../../../app/services/recommendation_templates.json) และตรรกะ [actionable_recommendations.py](../../../app/services/actionable_recommendations.py) ไม่ได้เรียกโมเดลสร้างข้อความที่เสียเงิน

**เงื่อนไขก่อนเป็นข้อเสนอ:** รับหมวดแล้ว, มีข้อความตรวจได้, ยังไม่พบประเด็นนั้นเมื่อรวมคำพ้อง, เกี่ยวข้องกับสิ่งที่ผู้ใช้พูด, มีหลักฐานอย่างน้อย 2 คลิปจาก 2 ช่อง พร้อม URL/วันที่/ข้อความตรวจสอบได้

ลำดับสำคัญใช้ความเกี่ยวข้องก่อน ตามด้วยสัดส่วนคลิปสนับสนุน จำนวนช่อง และความถี่ข้อความ เลือก **ไม่เกิน 3 ข้อหลัก** เพื่อให้ทำตามได้ นี่เป็นขีดจำกัดจำนวนข้อแนะนำที่แสดง ไม่ใช่หยุดอ่านข้อความหลังพบ 3 คำ

| สถานะ | ไม่ควรตีความผิดว่า |
|---|---|
| ตรวจพบแล้ว | ไม่ได้แปลว่าอธิบายได้ดีมาก เพียงมีข้อความตรงหลักฐาน |
| ยังไม่ตรวจพบ | ไม่ได้ยืนยันว่าไม่ได้พูดจริง หาก ASR ตกหล่นต้องฟังคลิปตรวจ |
| ตรวจไม่ได้ | ไม่ใช่ “ขาดเรื่องนั้น” ระบบไม่มี input พอประเมิน |
| ไม่มีประเด็นเพิ่มที่มีหลักฐานพอ | ไม่ใช่คลิปสมบูรณ์แบบ อาจเพราะสิ่งที่พบ/คลิปอ้างอิงยังไม่พอ |
| ข้อมูลอ้างอิงไม่พอ | ไม่ใช่ error ที่ควรแก้โดยใส่คำแนะนำสุ่ม |
| งดคำแนะนำเฉพาะหมวด | หมวดยังตรวจรับไม่ได้ จึงไม่เลือก Dataset ผิดหมวดไปสร้างเหตุผล |

“คัดลอกประโยคตัวอย่าง” เป็นบทพูดเสนอให้ปรับ ไม่ใช่ผลทดสอบจริง; ผู้ใช้ต้องแทนผลวัดที่ตนทำเอง และใช้เฉพาะฟังก์ชันที่สินค้ารุ่นนั้นมี

### ความยาวคลิปที่แนะนำ

ไม่ใช้ความยาวคลิปเดียวหรือเลขตายตัว: คัดคลิปหมวดเดียวกันที่ผ่านเงื่อนไขอ้างอิง มี duration จาก YouTube metadata และอยู่ในกลุ่มอ้างอิงความยาวไม่เกิน 5 นาที แล้วต้องมีอย่างน้อย **10 ตัวอย่าง** เป้าหมาย 15

- Median: เรียงความยาวจากน้อยไปมากแล้วเลือกตรงกลาง เพื่อลดผลของคลิปที่ยาวผิดกลุ่ม
- P25-P75: ช่วงครึ่งกลางของตัวอย่าง ไม่ใช่ช่วงรับประกันความสำเร็จ
- ถ้าไม่พอ ให้สถานะ “หลักฐานไม่เพียงพอ” ไม่มีการใส่เลขสมมุติให้ดูแม่น
- เกณฑ์ 5 นาทีของกลุ่มอ้างอิง duration ยังเป็นสัญญาข้อมูลใน `dataset_contract.py`; เปลี่ยน upload limit ไม่ได้เปลี่ยนกลุ่มอ้างอิงหรือความยาวข้อมูลฝึกเดิมอัตโนมัติ
- นี่คือความยาวของคลิปอ้างอิงที่มีอยู่ ไม่ใช่พิสูจน์ว่าเป็น “ความยาวที่ดีที่สุดบน YouTube” และยังต้องระวังชนิด Short-form กับรีวิวทั่วไป

ตรวจ profile วันที่ 4 ต.ค.: Phone มี 14 ตัวอย่าง Median 112 วินาที, Camera 33 ตัวอย่าง Median 79 วินาที, Laptop 24 ตัวอย่าง Median 52 วินาที จึงมีหลักฐานความยาวถึงขั้นต่ำแล้ว แต่ **ไม่ใช่เลขที่ระบบควรแนะนำให้คลิป Unknown** และไม่ใช่ตัวเลขแทนคลิปรีวิวทุกความยาว

### 3. เพราะอะไรจึงแนะนำ

เปิดหลักฐานแล้วดูจำนวนคลิป จำนวนช่อง ข้อความที่พบ URL, Dataset ID, วันที่เผยแพร่ วันที่เก็บสถิติ และเวอร์ชันการวิเคราะห์ เมื่อไม่มีเวลาใน Transcript ต้นแบบ ส่วนนี้จะไม่มี Timestamp แทนที่จะเดา

**วิธีคัดคลิปอ้างอิง:** ผ่าน Review, มีแหล่ง/Transcript/หมวดและสถิติที่ใช้ได้, อยู่ `train`, ได้สิทธิ์ใช้อ้างอิง และไม่ซ้ำวิดีโอ/ช่อง/ข้อความกับ Validation หรือ Test การมีอยู่ใน `dataset_contents` ไม่ได้แปลว่าใช้ได้ทุกแถว

ในคลิปที่มีค่าการวัดชนิดเดียวกัน คัดกลุ่มผลตอบรับสูงประมาณ 40% ด้านบน โดยพยายามใช้ไม่น้อยกว่า 10 เมื่อมีพอ ไม่ใช่เฉพาะคลิป Top 50 ของ Dashboard

```text
ค่าเฉลี่ยวิวสะสมต่อวัน = ยอดวิว / max(อายุคลิปถึงวันที่เก็บสถิติเป็นวัน, 1)
อัตราปฏิสัมพันธ์ = (ไลก์ + ความคิดเห็น) / max(ยอดวิว, 1)
คะแนนที่คำนวณ = ln(1 + วิวสะสมเฉลี่ยต่อวัน)
                 x (1 + min(อัตราปฏิสัมพันธ์ x 10, 1))
คะแนนคัดต้นแบบที่ใช้จริง = max(คะแนนที่คำนวณ, trend_score ที่บันทึกในแถว, 0)
```

`ln` ย่อความต่างของเลขขนาดใหญ่มาก ไม่ให้คลิปหลักล้านกลบทุกอย่าง; `min(...,1)` จำกัดผลของอัตราปฏิสัมพันธ์ สูตรนี้เป็น **เกณฑ์ที่ผู้พัฒนาเลือก** ไม่ใช่สูตรจัดอันดับของ YouTube และวิวสะสมหารอายุไม่ใช่ความเร็วการโตล่าสุด

ข้อควรระวังของ implementation ปัจจุบัน: `trend_score` เดิมยังมีผลหากสูงกว่าสูตรคำนวณ จึงไม่ควรบอกว่าทุกแถวถูกเลือกด้วยสูตรใหม่เพียงอย่างเดียว ต้องตรวจที่มาและสเกลของคะแนนเดิมด้วย การตรวจรอบนี้บันทึกข้อจำกัดไว้ ไม่ได้เปลี่ยนวิธีคัดต้นแบบย้อนหลัง

**คะแนนหัวข้อสำหรับ Keyword Gap:**

```text
45% x สัดส่วนคลิปที่พูดถึง
+ 25% x ความถี่หลังลดน้ำหนักการพูดซ้ำและปรับเทียบหัวข้ออื่น
+ 30% x สัดส่วนน้ำหนักผลตอบรับของคลิปที่พูดถึง
```

เช่น ในกลุ่ม 20 คลิปมี 10 คลิปพูดเรื่องชาร์จ สัดส่วนคลิปคือ 10/20 = 0.5 ส่วนความถี่ใช้ผลรวม `ln(1+จำนวนครั้ง)` เทียบค่าสูงสุดในชุด และน้ำหนักคลิปถูกปรับช่วง 1-3 ไม่ใช้ยอดวิวจำนวนมหาศาลคูณตรง ๆ

ขั้นนี้จัดอันดับหลักฐานของหัวข้อ จากนั้นคำแนะนำแบบลงมือทำยังต้องตรวจว่าเกี่ยวข้องและผู้ใช้ยังไม่พูดจริง อย่าสับสนว่าคะแนน Keyword กับอันดับคำแนะนำคือสูตรเดียวกันทั้งหมด

### หลักฐานเปรียบเทียบแบบเข้มขึ้น

[topic_comparisons.py](../../../app/services/topic_comparisons.py) แยกกลุ่ม “พบหัวข้อ” กับ “ไม่พบ” ภายในช่อง/หมวด/รูปแบบ/ช่วงอายุ/ช่วงความยาวและชนิด metric ที่เทียบกันได้ ใช้คลิปทั่วไปด้วย ไม่ได้ใช้เฉพาะกลุ่มผลตอบรับสูง

ต้องมีอย่างน้อย 10 คลิปต่อฝั่งและ 5 ช่องที่มีทั้งสองฝั่ง จึงรายงานความแตกต่างเชิงพรรณนาได้; ช่วงความไม่แน่นอนต้องมีอย่างน้อย 10 ช่อง ใช้ bootstrap 2,000 รอบ ระดับ 95% หากไม่ถึงก็ไม่แสดงข้อสรุปเปรียบเทียบ

ใช้ค่ากลางผลต่างภายในช่องก่อน แล้วสรุประหว่างช่อง เพื่อไม่ให้ช่องใหญ่ช่องเดียวครองผล แสดงผลลบ/ไม่ชัดด้วย ไม่เลือกเฉพาะหัวข้อที่ดูดี และความสัมพันธ์ยัง **ไม่พิสูจน์สาเหตุ**

การโตของคลิปอ้างอิงต้องมีสถิติสองเวลาจริง โดยเป้าหมายเทียบประมาณ 24 ชั่วโมงและยอมรับช่วง 12-36 ชั่วโมง หากมีแค่ยอดสะสมครั้งเดียว ให้ตรวจไม่ได้ ไม่เอา “วิวต่อวันตลอดอายุคลิป” มาแทน

### ไอเดียจากกระแสล่าสุด

แยกจากข้อความใน Transcript ของคลิปอ้างอิง ใช้ชื่อ/คำอธิบาย/คำค้นที่เกี่ยวข้องกับคลิปผู้ใช้ และระบุแหล่งกับเวลา โค้ดกำหนด Snapshot อายุไม่เกิน 24 ชั่วโมง, คลิป YouTube อายุไม่เกิน 7 วัน, คำค้นใช้หน้าต่างอายุ 48 ชั่วโมงตาม field ที่มี

ข้อจำกัดเวลา Google ตามบท Dashboard ยังใช้บังคับ: ถ้าไม่มีเวลาเริ่มกระแสจริง ห้ามอ้างว่านโยบายตัวเลขนี้ยืนยันอายุข่าวได้ เป็นเพียงเงื่อนไขกรองข้อมูลที่เก็บมา ไม่ใช้ข้อความชื่อคลิปอ้างว่ามีคนพูดประโยคนั้นในเสียง

## บันทึกแผนและเทียบฉบับแก้ไข

เลือก “นำไปปรับ” แล้วบันทึกพร้อมหมายเหตุ ไม่ได้ถือว่าปรับเสร็จ ระบบเก็บ `selected_advice_ids` และ fingerprint ของคำแนะนำใน `clip_revision_plans`; ถ้าหน้าเก่ากับผลใหม่ขัดกันต้องให้ตรวจ ไม่ทับเงียบ ๆ

อัปโหลดฉบับแก้ไขต้องเชื่อม parent clip และแผนเดิม ข้อมูลใน `clip_revision_comparisons` ใช้เทียบหัวข้อที่เลือกว่าตรวจพบแล้วหรือยัง พร้อมข้อความ/เวลา ตรวจความเข้ากันได้ของวิธีวิเคราะห์ และรายงานกรณีถอดเสียงต่างกัน ผลคือ **การเปลี่ยนแปลงเนื้อหา** ไม่ใช่คะแนนว่าคลิปใหม่จะดังขึ้น

ส่วนนี้มี automated/API fixture tests รองรับ แต่รอบตรวจวันที่ 3 ต.ค. **ยังไม่ยืนยัน positive workflow จากคำแนะนำจริงของโมเดลที่ผ่านรับรอง** เพราะ Active Model ถูกระงับคำแนะนำอยู่ ต้องไม่ใช้ fixture แทนหลักฐานคุณภาพโมเดล

## หน้า “ไอเดียและประวัติ”

อ่านผลที่บันทึกของผู้ใช้ที่ Login เท่านั้น เลือกหมวด/เรียงลำดับ/เปิดผลเก่าได้ ไม่วิเคราะห์ใหม่เมื่อกดดู หาก Dataset หรือโมเดลปัจจุบันเปลี่ยน ผลเก่าต้องยังแสดงคำแนะนำและหลักฐานที่บันทึก ณ วันนั้น

กราฟรายวัน/รายเดือนนับ **ผลวิเคราะห์ที่บันทึกสำเร็จ** จาก `analysis_results` เชื่อมเจ้าของใน `user_contents` ใช้วันตามเวลาไทย ตัวเลขไม่รวมงานล้มเหลวและไม่ใช่ยอดเข้าชมเว็บไซต์ ส่วนสัดส่วนหมวดคือหมวดผลวิเคราะห์ ไม่ใช่หมวดที่กำลังนิยมบน YouTube

## บันทึกอะไรที่ไหน

| ขั้น | ตาราง/ไฟล์ |
|---|---|
| ไฟล์อัปโหลด | โฟลเดอร์ `videos/` และ path ใน `user_contents` |
| เจ้าของ ชื่อคลิป Raw/Cleaned Transcript | `user_contents` |
| Keyword ที่พบ | `keywords` + `content_keywords` |
| หมวด Model ID และผลเต็ม | `analysis_results`; `summary` เป็น JSON ขนาดใหญ่ ไม่ใช่แค่ข้อความสั้น |
| คำแนะนำสำหรับการอ่านรูปแบบเดิม | `recommendations`; ผลเต็มและหลักฐาน frozen อยู่ใน `analysis_results.summary` ด้วย |
| แผนปรับคลิป | `clip_revision_plans` |
| งาน/ผลเทียบฉบับแก้ไข | `clip_revision_comparisons` |
| เหตุการณ์บันทึก | `system_logs` |

**ข้อจำกัดโครงสร้างงาน:** คิววิเคราะห์ปกติปัจจุบันใช้หน่วยความจำของ Backend หากปิดระหว่างวิเคราะห์ งานยังไม่เสร็จอาจหาย ต้องไม่สัญญาว่ามี durable queue แล้ว แต่ผลที่ commit เข้า DB สำเร็จยังอยู่และทดสอบหลังรีสตาร์ตแล้ว
