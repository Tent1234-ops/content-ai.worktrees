# 3. หน้า Admin และโมเดลที่ฝึกจริง

[กลับสารบัญ](README.md)

Admin ใช้ Login หน้าเดียวกับผู้ใช้ แต่ Backend ตรวจ role อีกชั้น ปัจจุบันมี 7 หน้าด้านล่าง ไม่มี Admin Console รวมลิงก์และไม่มีหน้ารายงานเปรียบเทียบ TikTok ที่แสดงเสมือนมีข้อมูลจริง

## 3.1 จัดการผู้ใช้: `/admin-users`

ค้นผู้ใช้/อีเมล กรอง role/สถานะ เพิ่มบัญชี แก้ข้อมูล เปลี่ยน role ระงับบัญชี ถอน session และลบบัญชีโดยยืนยันได้ ระบบป้องกันการทำให้ไม่มี Admin ที่ใช้งานได้และการจัดการตนเองในกรณีที่ไม่ปลอดภัย

| ข้อความ | หมายถึง |
|---|---|
| Admin / User | สิทธิ์ใช้งาน ไม่ใช่หมวดคอนเทนต์ |
| ใช้งาน / ระงับ | บัญชีเข้าใช้ได้หรือไม่ การระงับไม่เท่ากับลบ Dataset |
| คลิปที่บันทึก / ผลวิเคราะห์ / หัวข้อที่ติดตาม | จำนวนกิจกรรมของบัญชีนั้น ไม่ใช่ยอด engagement YouTube |
| รายวัน / รายเดือน | สรุปผลบันทึกตามปฏิทินไทย ใช้ดูการใช้งาน ไม่ได้วิเคราะห์ความดังของผู้ใช้ |
| ออกจากระบบทุกอุปกรณ์ | ยกเลิก session ที่บันทึกไว้ |
| ลบ | เป็นการกระทำจริงที่กระทบข้อมูลส่วนตัว ต้องตรวจชื่อยืนยัน ไม่ใช้แทนปุ่มระงับชั่วคราว |

ข้อมูลอยู่ `users`, `user_contents`, `analysis_results`, `followed_topics`, `notifications`, `user_trend_watch_sessions` และบันทึกเหตุการณ์ใน `system_logs`

## 3.2 นำเข้า Transcript: `/admin-transcript-import`

รองรับไฟล์ Markdown หรือวางข้อความ พร้อม URL YouTube หมวดที่เสนอ ภาษา ประเภทคำบรรยาย และวัตถุประสงค์การเก็บ เช่น ข้อมูลจำแนกหมวด/คลิปผลตอบรับสูง

NotebookLM เป็นเครื่องมือภายนอกที่ใช้ช่วยเตรียมข้อความ **ไม่ใช่โมเดลจำแนกที่เว็บไซต์กำลังใช้** การนำเข้าไม่ได้เท่ากับตรวจแล้วถูกทั้งหมด และไม่ได้ฝึกโมเดลทันที

```text
ไฟล์/ข้อความ + URL + หมวดที่เสนอ
-> ตรวจรูปแบบ/ข้อมูลต้นทาง/ความซ้ำ
-> candidate ใน dataset_contents + รอบใน dataset_collection_runs
-> คิว Review
-> อนุมัติพร้อมหมวดจริง/คุณภาพ
-> จึงพิจารณาว่าเข้า Train/Validation/Test หรือคลิปอ้างอิงได้หรือไม่
```

“หมวดที่เสนอ” คือข้อเสนอของผู้เก็บ ยังไม่ใช่ label ที่ผ่านตรวจ; “Transcript ทั้งคลิป” คือขอบเขตข้อความที่นำเข้า ไม่ได้แปลว่ามี Timestamp; “ข้อมูลจำแนกหมวด” เน้นตัวอย่างหลากหลาย ส่วน “คลิปผลตอบรับสูง” บอกวิธีคัดเลือก ไม่พิสูจน์เหตุให้ยอดสูง

เก็บรหัสวิดีโอ/ช่อง แหล่งข้อมูล เวอร์ชัน วันที่เก็บ และ hash ข้อความไว้ย้อนตรวจ ไม่ใช้ทุกแถวในฐานข้อมูลเป็น Train รวม ๆ

โค้ด: [หน้า Import](../../../frontend_flutter/lib/screens/admin_transcript_import_screen.dart), [บริการนำเข้า/Review และ provenance](../../../app/services/youtube_cc_dataset.py)

## 3.3 ตรวจ Dataset: `/admin-dataset-review`

เปิด candidate อ่าน Transcript และต้นทาง ตัดสินหมวด/คุณภาพ อนุมัติหรือปฏิเสธ พร้อมหมายเหตุ มีอนุมัติแบบกลุ่มแต่ยังต้องผ่าน validation ของแต่ละรายการ ไม่ใช่ข้ามการตรวจคุณภาพ

| คำ | ความหมาย |
|---|---|
| รอตรวจ | เข้าระบบแล้วแต่ยังไม่ควรเป็นข้อมูลฝึก/อ้างอิงที่เชื่อถือ |
| อนุมัติ | ผู้ตรวจรับข้อความและ label ตามเงื่อนไข ไม่ได้แปลว่าคลิปนั้นดัง |
| ปฏิเสธ | ไม่รับตัวอย่างนี้สำหรับวัตถุประสงค์ที่กำหนด เก็บเหตุการณ์ไว้ตรวจย้อน |
| Transcript คุณภาพดี / ใช้งานได้ | การประเมินคุณภาพข้อความ ไม่ใช่ classification confidence |
| ความครอบคลุมที่ตรวจสอบแล้ว | จำนวนหมวด/ช่อง/ชุดข้อมูลที่ผ่านเงื่อนไขจริง ไม่ใช่จำนวนไฟล์ในโฟลเดอร์ |

แก้ไข `dataset_contents`; เก็บผู้ตรวจ หมวดที่เสนอ/หมวดที่ตรวจรับ คุณภาพ และเหตุผลใน `dataset_review_events` พร้อม `system_logs` ส่วนการแก้ภายหลังจากหน้า Datasets ใช้ audit ใน `system_logs` ไม่ได้หมายความว่ามีสำเนา Transcript ก่อนแก้ทุกเวอร์ชันในตาราง Review

โค้ดหน้า: [admin_dataset_review_screen.dart](../../../frontend_flutter/lib/screens/admin_dataset_review_screen.dart)

## 3.4 จัดการ Dataset: `/admin-datasets`

ใช้ดูรายการ แก้ชื่อ/Transcript/หมวด/Metadata เพิ่มข้อมูลรอตรวจ ดูความพร้อม วางแผนเก็บเพิ่ม และถังขยะ/กู้คืน

ตอนนี้แก้ Transcript และ label ภายหลังได้แล้ว ไม่ใช่ข้อจำกัดรุ่นเก่าที่เปลี่ยนเพียงชื่อ Category แต่ taxonomy ไม่เปลี่ยน Backend ดูแล hash และ taxonomy ที่เกี่ยวข้อง มีการตรวจความซ้ำ/สิทธิ์ใช้ และเก็บ audit

**แต่แก้ Database ไม่ได้เปลี่ยนโมเดลที่ฝึกไปแล้ว:** โมเดลเป็นไฟล์แยก ต้องฝึกใหม่และผ่านเกณฑ์ก่อน Activate ผลผู้ใช้ที่บันทึกไว้ก็ไม่ควรเปลี่ยนย้อนหลังตามการแก้ Dataset

| หัวข้อ | ประโยชน์ |
|---|---|
| รายการข้อมูล | ตรวจต้นฉบับและแก้ข้อมูลผิด |
| บทบาทและความพร้อมของข้อมูล | แยกใช้ฝึก / ใช้อ้างอิง / ประเมิน / เทรนด์ ว่าแต่ละรายการผ่านหรือขาดอะไร |
| เหตุผลที่ยังไม่ใช้เป็นคลิปอ้างอิง | อาจอยู่ Test, ขาดวันที่, ไม่มี source, สถิติไม่ครบ ไม่ใช่มี Transcript แล้วใช้ได้ทันที |
| แผนเก็บข้อมูล | บอกว่าขาดหมวด ช่อง หรือกลุ่มเปรียบเทียบใด ไม่ให้เก็บคลิปอะไรก็ได้เพื่อเติมจำนวน |
| ถังขยะ | Soft delete: หยุดใช้กับงานใหม่ แต่รักษาประวัติ/หลักฐานผลเก่า |
| กู้คืน | ตรวจเงื่อนไขใหม่ ไม่รับรองว่าได้สิทธิ์ฝึกคืนทันทีทุกแถว |

ยอดวิว/ไลก์/ความคิดเห็นใช้เป็น metadata และหลักฐานการคัด/เทียบคลิป ไม่ใช่ input ตัวจำแนกหมวด ทุก field ไม่จำเป็นต้องถูกป้อนเข้า classifier เพื่อถือว่ามีประโยชน์

โค้ด: [หน้า Datasets](../../../frontend_flutter/lib/screens/admin_datasets_screen.dart), [Routes](../../../app/routes/admin.py), [ความพร้อม](../../../app/services/dataset_readiness.py), [สิทธิ์ใช้งานข้อมูล](../../../app/services/dataset_eligibility.py)

## 3.6 เทรนโมเดล AI: `/admin-training`

### ต้องแยกสามคำนี้ก่อน

**Train** = เรียนรู้จากตัวอย่าง, **Evaluate** = ตรวจคะแนนกับคำตอบจริง, **Activate** = เลือกไฟล์โมเดลที่ผ่านเงื่อนไขไปให้ผู้ใช้งานใหม่ เริ่ม Train ไม่ได้ Activate อัตโนมัติ

### แบ่งตามช่องหมายถึงอะไร

ตัวอย่าง: ช่อง A รีวิวโทรศัพท์ 20 คลิป ถ้าเอา 18 คลิปฝึกและ 2 คลิปสอบ อาจง่ายเพราะสไตล์คำพูดคล้ายกัน จึงกำหนดให้คลิปจากช่องเดียวกันอยู่ชุดเดียวกัน ไม่กระจายข้ามชุด แม้ช่องนั้นรีวิวหลายหมวด

ระบบใช้ Channel ID สร้าง hash เพื่อจัดกลุ่มแบบทำซ้ำได้ เป้าหมายประมาณ 70/15/15 แต่ **ไม่จำเป็นต้องได้จำนวนคลิปตรง 70/15/15** เพราะแบ่งทั้งช่อง ไม่ใช่สุ่มทีละคลิป

วันที่4ต.ค.เพิ่มทะเบียนแผน `scope-holdout-20261004-v1` เพื่อแก้Unknownที่ถูกจัดไว้ฝั่งTrainมากเกินไป แผนย้ายพร้อมกันทั้งช่องโดยใช้จำนวนและidentityก่อนดูคะแนน คงValidation/Testเดิมไว้ และฝึกใหม่ทั้งหมด แผนที่บันทึกมีสิทธิ์เหนือhashสำหรับช่องนั้น ผลนี้เป็นrepartitioned benchmark ไม่ใช่ข้อสอบใหม่จากภายนอก

| ชุด | เอาไว้ทำอะไร | ห้ามทำอะไร |
|---|---|---|
| Train | เรียนรู้คำและน้ำหนัก; ใช้ grouped CV ภายในชุดนี้เลือกตัวเลือกโมเดล | อย่าเอาข้อสอบ Test มารวม |
| Validation | ตรวจนโยบายการรับ/ปฏิเสธหมวด โดยมี Unknown มาช่วยเลือกเกณฑ์ | ไม่ใช้ฝึก classifier รอบสุดท้ายในโค้ดนี้ |
| Test | ตรวจผลตามวิธีที่กำหนดแล้ว | ไม่ดูผิดแล้วแก้ threshold ให้ผ่านข้อเดิมจนเรียกว่า Test ใหม่ |

หลักการกลุ่มตัวอย่างและการกัน Test สอดคล้องกับแนวทาง cross-validation ของ [scikit-learn](https://scikit-learn.org/stable/modules/cross_validation.html) แต่ตัวเลขแบ่งและเกณฑ์เป็นการออกแบบของโปรเจคนี้

### ข้อมูลรอบวันที่ 4 ต.ค.

| หมวด | Train | Validation | Test | รวม | ช่องไม่ซ้ำภายในหมวด |
|---|---:|---:|---:|---:|---:|
| Phone | 63 | 12 | 5 | 80 | 27 |
| Camera | 61 | 13 | 6 | 80 | 43 |
| Laptop | 54 | 5 | 26 | 85 | 23 |
| รวมสามหมวด | 178 | 30 | 37 | 245 | 83 ช่องรวมหลังตัดซ้ำ |

Unknownมี42: สำรอง2, Validation10จาก9ช่อง, Test30จาก17ช่อง ชุดสำรอง **ไม่ได้ fit เป็นหมวดที่สี่** จำนวนชุดประเมินครบแล้ว แต่ยังต้องดูคะแนนไม่ใช่ยอดรวมอย่างเดียว

### โมเดลอ่านอะไรและเรียนรู้อะไร

`ClassificationExample.model_text` ใช้ **Transcript** ไม่ใช้ชื่อไฟล์/ยอดวิวเป็นตัวทายหมวด กลุ่ม TF-IDF สร้าง feature สองแบบรวมกัน: คำหรือคู่คำ และกลุ่มตัวอักษรติดกัน 3-5 ตัว ช่วยรับภาษาไทยและรูปคำที่หลากหลาย

TF-IDF แบบเข้าใจง่าย: คำที่พบบ่อยในคลิปหนึ่งอาจมีน้ำหนัก แต่คำที่พบทั่วไปแทบทุกคลิปจะลดความเด่น ค่าคำศัพท์และการปรับตัวเลขเรียนจาก Train เท่านั้น จึงไม่ควรสร้าง vocabulary จากทั้ง Train และ Test ก่อนแบ่ง

| ตัวที่ฝึก | วิธีคิด |
|---|---|
| Complement Naive Bayes | เรียนรู้ว่าน้ำหนักคำสัมพันธ์กับแต่ละหมวดอย่างไร เหมาะเป็น baseline ข้อความ |
| Tuned Logistic Regression | เรียนรู้น้ำหนัก feature เพื่อแยกหมวด ทดลอง C=0.5/1/2/4 ด้วย grouped CV |
| Calibrated Linear SVM | เรียนรู้เส้นแบ่งหมวด แล้วปรับคะแนนให้มีรูปแบบความเชื่อมั่นที่ใช้งานต่อได้ |
| Multilingual embeddings + Logistic Regression | ใช้โมเดลหลายภาษาที่ฝึกไว้แล้วแปลงข้อความเป็นเวกเตอร์ แล้วฝึกตัวจำแนก ไม่ใช่ fine-tune Transformer ใหญ่ทั้งตัว |

**Grouped CV 5 รอบ:** ภายใน Train178คลิป แบ่งตามช่องเป็นกลุ่มย่อย หมุนกลุ่มที่เป็นข้อสอบแต่ละรอบ แล้วรวมผลทายที่เกิดตอนคลิปไม่ได้อยู่ในส่วน fit ของรอบนั้น เพื่อไม่ตัดสินจาก split เดียว

### รู้ได้อย่างไรว่าเป็น Unknown

Classifier ทายได้เพียงสามหมวด จึงต้องมีนโยบายยอมรับแยก: คะแนนเชื่อมั่นถึงเกณฑ์หรือไม่ และข้อความคล้ายตัวอย่าง Train ของหมวดที่ทายพอหรือไม่ ขีดแบ่งความคล้ายเลือกด้วย Validation ทั้งสามหมวดและ Unknown ไม่ใช่เขียนว่าเจอคำว่า “หูฟัง” แล้วบังคับแก้หมวดภายหลัง

ตอนนี้Unknown Validationครบ10แล้ว และได้ลองเกณฑ์similarityจริง แต่ไม่มีเกณฑ์ที่ผ่านทุกเงื่อนไขพร้อมกัน จึงเป็น `failed_validation` ไม่ใช่ข้อมูลไม่ครบ ตัวอย่างSVMรับLaptopถูก1/5 แม้ยังไม่บังคับsimilarity; เมื่อเพิ่มเกณฑ์จนปฏิเสธUnknownได้9/10 กลับรับสามหมวดถูกเพียง18/30 ระบบจึงยังงดคำแนะนำเฉพาะหมวด

### คะแนนแต่ละตัวแปลว่าอะไร

| คะแนน | คำอธิบายและตัวอย่าง |
|---|---|
| Accuracy | ทายถูก / จำนวนตัวอย่างทั้งหมด เช่น ถูก 9 จาก 10 = 90% |
| Precision ของ Phone | ในคลิปที่โมเดลบอกว่า Phone มี Phone จริงกี่ส่วน |
| Recall ของ Phone | ใน Phone จริงทั้งหมด โมเดลรับว่า Phone ถูกกี่ส่วน |
| F1 ของหมวด | ค่ารวม Precision และ Recall: `2 x P x R / (P + R)` |
| Macro F1 | คำนวณ F1 ทีละหมวดแล้วเฉลี่ยให้น้ำหนักหมวดเท่ากัน จึงไม่เท่ากับ Accuracy เสมอ |
| Minimum class recall | Recall ของหมวดที่แย่ที่สุด ใช้กันโมเดลที่ภาพรวมดีแต่พลาดหมวดหนึ่งหนัก |
| Unknown recall | ในตัวอย่างนอกขอบเขตจริง ปฏิเสธได้กี่ส่วน ไม่ใช่ทาย Unknown ทุกอย่างแล้วถือว่าเก่ง |
| Sample size | จำนวนตัวอย่างที่ใช้คะแนนช่องนั้น ต้องดูควบคู่เสมอ |

`Validation Accuracy` กับ `Test Accuracy` ใช้สูตรเดียวกันแต่คนละชุดข้อมูล จึงต่างกันได้ และ `Confidence 98%` ในคลิปหนึ่งไม่ได้หมายถึง Test Accuracy 98%

### ผลเทรนล่าสุด

| ID | โมเดล | Grouped CV Accuracy | Grouped CV Macro F1 | Recall ต่ำสุด CV | เปิดใช้ได้ |
|---|---|---:|---:|---:|---|
| 41 | Calibrated Linear SVM | 92.70% | 94.96% | 90.16% | ยังไม่ได้ |
| 40 | Logistic Regression | 90.45% | 94.55% | 87.30% | ยังไม่ได้ |

| 39 | Complement NB | 79.78% | 81.65% | 65.08% | ยังไม่ได้ |

นี่คือคะแนน CV จากรายงานก่อนใช้นโยบายปฏิเสธใหม่ที่ยังไม่พร้อม ไม่ใช่คะแนนการใช้งานครบวงจร SVM เป็นอันดับแรกตามวิธีเลือกที่กำหนด ไม่ได้เลือกเพราะดู Test แล้วสูงสุด

การประเมินหลังบังคับนโยบายที่ยังไม่ผ่านคืนUnknownทุกคลิป ทำให้Accuracy/F1ของสามหมวดเป็น0 **แปลว่าระบบงดรับหมวดทั้งหมด ไม่ใช่ว่าโมเดลเรียนรู้ไม่ได้เลย** Unknown recallในสภาพนี้เป็นnull ไม่รายงาน100%จากการปฏิเสธทุกอย่าง และไม่ใช้raw Testเลือกตัวมาเปิดใช้

### ค้างอะไร ต้องเก็บอีกเท่าไร

**ไม่ขาดจำนวนUnknownตามเกณฑ์เดิมแล้ว** คำแนะนำให้หาเพิ่ม33คลิปในรายงาน3ต.ค.ถูกแทนด้วยผลจัดชุด4ต.ค. ห้ามย้ายชุดอีกหลังดูคะแนนเพื่อให้ผ่าน ขั้นถัดไปตรวจLaptopในTrain/ValidationและวิธีปฏิเสธUnknown โดยไม่ใช้Testปรับระบบ และยังต้องกันfresh external evaluationแยกต่างหาก ดู[Handoffล่าสุด](../../implementation/scope-holdout-20261004-handoff.md)

### หลัง Train ได้ไฟล์แล้วเกิดอะไรต่อ

**ข้อยกเว้นสำหรับพรีเซนต์ 5 ต.ค.:** ผู้ใช้อนุญาตเปิดHybrid#43แบบ`presentation_only`
48ชั่วโมง แม้ยังไม่ผ่านเกณฑ์ ไม่ใช่การActivateผ่านปุ่มปกติ ไม่เปลี่ยนmetricsเป็นผ่าน
และยังมีคำเตือน/ตรวจUnknown/วันหมดอายุ ดู[รายละเอียดโหมดสาธิต](../../implementation/presentation-model-20261005-handoff.md)

1. บันทึก manifest ระบุ Dataset IDs, split, fingerprint และเวอร์ชันที่ใช้
2. บันทึก `model.joblib`: ตัวแปลงข้อความ + ตัวจำแนก + metadata/นโยบายที่เกี่ยวข้อง ไม่ใช่โค้ดโมเดลใหม่หนึ่งไฟล์ `.py`
3. Reload ไฟล์ที่บันทึกแล้วลองทาย เพื่อกันกรณีฝึกผ่านแต่ไฟล์ใช้ไม่ได้
4. บันทึก registry ใน `classification_models`, metrics ใน `model_evaluation_metrics`, งานใน `model_training_runs`
5. Admin อ่านผลและกด Activate เฉพาะที่ Backend ตรวจว่าผ่าน การเปลี่ยน active มีผลกับงานใหม่
6. Analyze ครั้งต่อไปอ่าน Active Model และโหลด artifact ตามรุ่น/ข้อมูลอ้างอิงที่บันทึกไว้ ไม่ได้เปิดไฟล์ฝึก `.py` มาฝึกใหม่ทุกครั้ง
