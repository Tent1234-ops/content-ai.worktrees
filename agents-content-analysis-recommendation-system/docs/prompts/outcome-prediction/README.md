# Outcome Prediction: แผนส่ง 19 ตุลาคม 2026

สถานะ: ชุด Prompt มอบหมายงาน จัดทำ 8 ตุลาคม 2026 ยังไม่ใช่รายงานว่าพัฒนา/ฝึก/ประเมินโมเดลนี้เสร็จแล้ว

ชุดนี้เป็น **Outcome Prediction Phase 1-7** แยกจาก Recommendation Roadmap และ Project Closeout รอบก่อน อย่านำสถานะผ่านของ Phase ชื่อคล้ายกันมาใช้แทนกัน

## เป้าหมายที่ตกลงให้เหมือนกัน

ตอบผู้ใช้ว่า **"ทำไมประเด็นนี้จึงน่าลองเพิ่ม"** ด้วยสามส่วน:

1. คลิปผู้ใช้ยังไม่พบประเด็นอะไร และควรเพิ่มเนื้อหาอย่างไร จาก Transcript จริง
2. คลิปอ้างอิงที่เทียบกันได้ให้หลักฐานอย่างไร รวมจำนวนคลิป ช่อง เวลา และข้อจำกัด
3. เมื่อข้อมูลและการประเมินผ่านจริง โมเดลแยกต่างหากประเมินโอกาสอยู่ในกลุ่มผลตอบรับสูงกว่าค่ากลางของ **ชุดอ้างอิงที่ระบุ** ไม่ใช่รับประกันยอดวิวเพิ่มหลังทำตาม

โมเดลจำแนก Phone/Camera/Laptop เดิมยังทำหน้าที่เดิม ไม่ใช้ Classification Confidence เป็นค่าทำนายผลตอบรับ ไม่เปลี่ยนเป็น LLM แต่งเปอร์เซ็นต์

รุ่นส่งนี้ใช้ **ยอดวิวสะสม ณ เวลาสังเกต ภายในกลุ่มอายุคลิปและรูปแบบใกล้เคียงกัน** เป็นเป้าหมายหลัก เป็นการประเมินเชิงสังเกตย้อนหลัง ไม่ใช่การทำนายยอดวิวใน 7 วัน ไม่ใช่ประมาณผลเชิงเหตุและผลของการเพิ่มหัวข้อ

อ่าน [ข้อตกลงกลาง](prediction-contract.md) ก่อนทุก Phase หากต้องเปลี่ยนความหมายนี้ต้องเสนอผลกระทบและขอผู้ใช้ยืนยัน ไม่ตีความเปลี่ยนเองระหว่างพัฒนา

## วิธีสั่ง Sol ทีละ Phase

เริ่มด้วยข้อความนี้:

```text
อ่าน docs/prompts/outcome-prediction/README.md
และ docs/prompts/outcome-prediction/prediction-contract.md
และ docs/prompts/outcome-prediction/phase-1-readiness-and-protocol.md
ตรวจโค้ดและข้อมูลปัจจุบันก่อนลงมือ แล้วทำให้ครบเฉพาะ Outcome Prediction Phase 1
ต่อยอดระบบเดิม ไม่สร้างระบบซ้ำ ไม่ลดเกณฑ์เพื่อให้ผ่าน และไม่แต่งข้อมูล
บันทึกงานที่เสร็จ/ค้าง คำสั่งทดสอบ และหลักฐานใน Handoff ตามที่กำหนด
หากติดข้อมูลหรือสิทธิ์ ให้ทำส่วนที่ไม่ติดให้จบและระบุ dependency ตามจริง
ไม่เริ่ม Phase ถัดไปอัตโนมัติ
```

ครั้งต่อไปเปลี่ยนชื่อไฟล์และเลข Phase อ่าน Handoff ก่อนหน้าด้วย ทุก Phase มีขอบเขต Tests และเกณฑ์ผ่านในไฟล์ ไม่ต้องส่งประวัติสนทนาทั้งหมด ไม่รับประกันว่า Agent ต่างรุ่นจะตัดสินใจตรงกันหากไม่มีการตรวจรับ

## จุดตรวจตัดสินใจ

- **9 ต.ค.:** Phase 1 ต้องตอบว่าใช้ข้อมูลอะไรได้ สิทธิ์ใช้งานยืนยันแล้วหรือยัง และต้องเก็บอะไรเพิ่ม ห้ามสั่ง "หาอีก 100 คลิป" โดยไม่มีรายการช่องว่าง
- **10 ต.ค.:** ต้องได้ Manifest ที่ใช้ได้หรือรายงาน No-go พร้อมจำนวนที่ขาด หากยังไม่มีข้อมูลก็เริ่มงาน Pipeline ด้วย Fixture ที่ระบุชัดได้ แต่ยังไม่ถือว่ามีโมเดลใช้งานจริง
- **12 ต.ค.:** ต้องทราบว่าโมเดลให้ประโยชน์เหนือ Baseline ใน Validation หรือไม่ หากไม่ผ่าน ให้แจ้งผู้ใช้ทันที ไม่ทดลองไม่สิ้นสุดจนกินเวลา UI
- **15 ต.ค.:** Freeze Candidate/Protocol ก่อนเปิด Test เก็บงาน UI และ States ให้ครบ
- **17 ต.ค.:** Freeze รุ่นส่ง ต้องมีคำตัดสินแยกสามส่วน ไม่เรียกทุกอย่างว่า "ผ่าน" เพราะ Test code ผ่าน

| สถานะ | สิ่งที่หมายถึง |
|---|---|
| Software complete | Pipeline/API/UI/การบันทึกทำงานและมี Tests |
| Prediction qualified | สิทธิ์ ข้อมูล Calibration และผลประเมินอิสระผ่านเฉพาะขอบเขตที่ระบุ |
| Utility evaluated | มีผู้ประเมินจริงว่าคำแนะนำเข้าใจง่ายและนำไปใช้ได้ |
| Engagement uplift proven | **อยู่นอกขอบเขตรุ่นนี้** ต้องมีการทดลองติดตามผลที่ออกแบบรองรับเหตุและผล |

หากผ่านแค่ Software และหลักฐานอ้างอิง ให้ส่งด้วยสถานะนั้นและระบุว่า Outcome Prediction ยังไม่ผ่าน ไม่ถือว่าบรรลุเป้าหมายโมเดลเต็มรูปแบบโดยอัตโนมัติ ต้องแจ้งผู้ใช้เพื่อตกลงขอบเขตส่ง ไม่ซ่อนปัญหาไว้ถึงวันสุดท้าย

## ฐานข้อมูลที่ทราบก่อนเริ่ม

ผลตรวจแบบอ่านอย่างเดียววันที่ 8 ต.ค. เป็นเพียง Baseline ที่ต้องตรวจซ้ำ:

- แถวหมวด Phone/Camera/Laptop ที่ยังใช้งาน 308: Train 209, Validation 52, Test 47
- Collection strategy: classification_diverse 246, recommendation_high_performance 61, ไม่ระบุ 1
- มีประวัติอย่างน้อยสองเวลาของ 186 Video IDs; Observation จำนวนมากไม่ใช่จำนวนคลิปอิสระ
- คลิปที่มี Observation ใกล้อายุ 7 วันมีน้อย ไม่ใช่หลักฐานเพียงพอทำโมเดลยอด 7 วัน
- ตัวเก็บสถิติเดิมเริ่มจากคลิปอ้างอิง ไม่ได้แปลว่า Validation/Test มีสถิติพร้อมแล้ว
- ผลตรวจ 7 ต.ค. พบ Active Classifier แบบ presentation_only หมดอายุ ต้องตรวจใหม่ ห้ามต่ออายุหรือข้าม Unknown Gate อัตโนมัติ

308 แถวไม่ใช่ 308 แถวที่ฝึก Outcome ได้ และ 47 Test ไม่ใช่ Fresh Outcome Test ที่ยืนยันแล้ว ต้องตรวจ Identity, ช่อง, สิทธิ์, เวลา, รูปแบบคลิป, การเคยใช้ปรับระบบ และการทับซ้อนก่อน

## กติกาการทำงานร่วมกัน

- ห้ามทำลายข้อมูล/งานค้าง ไม่ Reset/Drop/ล้าง Artifact ไม่แก้ Git pointer ที่เสียเอง
- ไม่ Train/Activate โมเดลจำแนกหมวดใหม่โดยพลการ Outcome Registry ต้องแยกหน้าที่จาก Classification Registry
- ใช้ FastAPI/SQLAlchemy, Flutter และ sklearn ที่มีอยู่ ไม่เพิ่ม Paid API, LLM, แหล่ง TikTok/Instagram หรือ Fine-tuning ในแผนนี้
- ขออนุมัติก่อน Activate โมเดลจริง เปลี่ยน Scheduler จริง หรือแก้ข้อมูลที่มีผลต่อการประเมิน งาน Fixture/DB ทดสอบต้องแยกจากข้อมูลผู้ใช้
- การเก็บข้อมูลเพิ่มใช้ API/แหล่งที่ได้รับอนุญาตและงบโควตาจริง ไม่เพิ่มงานหลายตัวดึงซ้ำกัน ไม่ทำ Scraping เพื่อเลี่ยงข้อจำกัด
- สิทธิ์ใช้ YouTube API Data ทำ Derived Metrics/ฝึกโมเดลต้องตรวจเป็น Dependency ไม่อนุมานว่า API ฟรีหรือโปรเจคจบได้รับยกเว้น
- ข้อความ/เวลา/จำนวน/ผลการทดลองต้องย้อนตรวจได้ Missing ไม่เท่ากับ 0, ไม่พบไม่เท่ากับตรวจไม่ได้, ผลลบต้องไม่ถูกซ่อน
- Prompt แต่ละ Phase จำกัดงานชัด ทำเฉพาะที่ได้รับมอบหมาย ห้ามเริ่ม Phase ถัดไปเอง

## สิ่งที่ผู้ใช้เตรียมควบคู่

- Phase 1 จะออก Gap list ก่อน จึงค่อยเก็บ Metadata/คลิปทั่วไป/ช่องใหม่ที่ขาด ไม่ต้องเดาจำนวน Transcript เพิ่มตอนนี้
- เตรียมหลักฐานสิทธิ์ใช้ข้อมูลและผู้รับผิดชอบยืนยันเงื่อนไข API; Agent ไม่สามารถยอมรับเงื่อนไขแทนเจ้าของโครงการ
- นัดผู้ประเมินจริงอย่างน้อย 3 คนไว้วันที่ 16-17 ต.ค. และเตรียมคลิปสำหรับ Live upload/ฉบับแก้ที่มีสิทธิ์ใช้
- ตัดสินใจเรื่อง Classifier ที่อาจ Block Live flow และการอนุมัติ Activate ผ่าน Workflow จริงก่อนวันตรวจรับ ไม่รอคืนก่อนส่ง

## Handoff และ Artifact

ทุก Phase สร้าง `docs/implementation/outcome-prediction-phase-N-handoff.md` โดยมี:

1. สถานะ Software / Data rights / Data / Prediction / Utility แยกกัน พร้อมเกณฑ์ที่ผ่าน/ไม่ผ่าน/ไม่ได้ตรวจ
2. ไฟล์ Tables Endpoints และ Migration ที่เปลี่ยน; สิ่งที่ตรวจแล้วนำกลับมาใช้
3. เวอร์ชัน Target/Protocol/Feature/Model/Split/Dataset/Observation cutoff และ SHA256
4. คำสั่งที่รันจริง Exit code ผล Tests หลักฐาน Live/Fixture/Human แยกชัด
5. งานที่ค้าง ผู้รับผิดชอบ สิ่งที่ขอผู้ใช้ และผลต่อกำหนดส่ง
6. ข้อมูล/บัญชีทดสอบที่สร้าง วิธีคืนค่า Rollback และขั้นตอนให้ Agent ถัดไปตรวจ
7. ข้อจำกัดที่ต้องแจ้งในหน้าเว็บ/พรีเซนต์ และ URL เมื่อมีการแก้ Web

เก็บหลักฐานใน `artifacts/outcome-prediction/phase-N/<run-id>/` ไม่วางรูป/log กระจัดกระจายที่ Root ห้ามแนบ API key, Password, Token หรือ Transcript ส่วนตัวในเอกสารพรีเซนต์

## แหล่งอ้างอิง

- [scikit-learn: Data leakage](https://scikit-learn.org/stable/common_pitfalls.html): แยกข้อมูลก่อนเรียนรู้ค่าจากข้อมูล
- [scikit-learn: Probability calibration](https://scikit-learn.org/stable/modules/calibration.html): คะแนนที่อยู่ในช่วง 0-1 ยังไม่ใช่หลักฐานว่าความน่าจะเป็นถูกต้อง
- [YouTube: Video statistics](https://developers.google.com/youtube/v3/docs/videos#statistics): ตรวจนิยามและที่มาของสถิติที่นำมาใช้
- [YouTube: Derived metrics policy](https://developers.google.com/youtube/terms/derived-metrics-policy) และ [Policy guide](https://developers.google.com/youtube/terms/developer-policies-guide): ตรวจเงื่อนไขการใช้ข้อมูล/การยอมรับข้อกำหนดที่เกี่ยวข้องก่อนใช้งานจริง

อ่านเงื่อนไขฉบับปัจจุบันใน Phase 1 การลิงก์เอกสารไม่เท่ากับได้รับอนุญาตแล้ว และเอกสารนี้ไม่ใช่คำวินิจฉัยทางกฎหมาย
