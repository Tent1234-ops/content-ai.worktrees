# แผนปิดโปรเจคก่อนส่ง 5 ตุลาคม 2026

ชุดคำสั่งนี้เป็น **Closeout Phase 1-6** ไม่ใช่ Recommendation Phase 5-7 เดิม และไม่ใช่คำสั่งให้สร้างระบบใหม่ทั้งหมด

สถานะเอกสาร: เป็นแผนและคำสั่งส่งต่อ ยังไม่ได้หมายความว่า Closeout Phase ใดผ่านแล้ว ต้องอ้าง Handoff/หลักฐานของแต่ละงานหลังลงมือจริง

ฐานแผน: `docs/implementation/acceptance-20260930.md` ตรวจจริงคืน 30 กันยายนถึง 1 ตุลาคม พบว่าเส้นทางเว็บ/ฐานข้อมูลทำงาน แต่คำแนะนำถูกงดเพราะ Active Model ไม่มี policy ปฏิเสธ Unknown ที่ผ่าน Validation

เป้าหมายผู้ใช้: ปิดการพัฒนาวันศุกร์ **2 ตุลาคม**, ใช้เสาร์ **3** และอาทิตย์ **4** ทำความเข้าใจและซ้อม, ส่งวันจันทร์ **5** ไม่รับประกันว่าฝึกโมเดลจะผ่านเกณฑ์ภายในกำหนดเพียงเพราะโค้ดทำเสร็จ

| Phase | งานหลัก | สิ่งที่ได้เมื่อจบ | เงื่อนไขต่อ |
|---|---|---|---|
| 1 | ล็อกขอบเขตและตรวจความพร้อม | ตารางขอบเขต/ข้อที่รอยืนยัน, สถานะโมเดลและรายการข้อมูลขาดที่ตรวจจากระบบ | งานที่รอผู้ใช้ต้องไม่ถูกตีเป็นผ่าน |
| 2 | ปิด Analysis และคำแนะนำ | ใช้โมเดลที่ผ่านเกณฑ์, แนะนำได้จากหลักฐาน, บันทึก/เทียบฉบับแก้ไขได้ตามจริง | ต้องมีข้อมูล/โมเดลที่ผ่านประเมิน ไม่ใช่แค่ UI แสดงผล |
| 3 | ปิด Workflow ผู้ใช้และ Admin | Follow/Notification/Scheduler/CRUD/Settings ทำงานต่อเนื่อง | ทำเพิ่มเฉพาะช่องว่างในขอบเขตที่ยืนยัน |
| 4 | เก็บ UI ทุกหน้าที่ส่ง | เว็บสม่ำเสมอ อ่านง่าย มีสถานะครบ ไม่มีปุ่มหลอก | ไม่เปลี่ยนวิธีคิดโมเดลระหว่างตกแต่ง |
| 5 | ตรวจรับรุ่นส่ง | รายงานผลจริงแยก software/model/utility, หลักฐานเดโม และรายการข้อจำกัด | ห้ามประกาศผ่านข้อที่ไม่ได้ทดสอบหรือถูกกั้น |
| 6 | เตรียมส่งและอธิบายระบบ | คู่มือเปิดระบบ/สำรอง/พรีเซนต์, รุ่นส่งที่ระบุได้และหลักฐานสะอาด | หลัง freeze แก้เฉพาะข้อผิดพลาดขวางเดโมพร้อม retest |

## กติกาทุก Phase

1. อ่าน acceptance report, review/handoff ของ Recommendation Phases 5-7 และโค้ดที่เกี่ยวข้องก่อนแก้ ข้อมูลในรายงานเป็น baseline ไม่ใช่ข้อเท็จจริงที่ไม่มีวันเปลี่ยน
2. รักษางานผู้ใช้และฐานข้อมูลเดิม ไม่ reset/drop ตาราง ไม่สลับโมเดลหรือเปลี่ยน Label เพื่อให้ demo ผ่าน ทดสอบ mutation ด้วยบัญชี/แถวที่แยกและไม่เข้า Train/Reference
3. อ่านค่าจาก Backend กลาง ไม่ hard-code Model #14, จำนวนข้อมูล หรือข้อความความพร้อมใน UI; Model #14 เป็นเพียงผลตรวจรอบก่อน
4. ไม่ปิด `classification_require_scope_validation` ไม่ลดเกณฑ์ตามคลิปผิด ไม่ให้ keyword rules ทายทับ Active Model ไม่แก้ artifact/metrics เพื่อปลอม qualification
5. Train/Validation/Test แยกตาม identity/channel ตาม contract; Test ไม่ใช้เลือก threshold/เลือกโมเดล/แก้กฎ คลิปที่ดูผลแล้วใช้ปรับระบบเป็น regression ไม่ใช่ fresh test อีก
6. แยก Transcript evidence, Metadata/trend ideas, และสถิติเปรียบเทียบ ไม่สร้างข้อความอ้างอิง Timestamp สเปกยอดวิว หรือผลประเมินที่ไม่มีจริง ไม่ใช้ confidence แทนคุณภาพคำแนะนำหรือ Engagement
7. ไม่ทำ Transformer fine-tuning, แหล่ง TikTok/Instagram ใหม่, ระบบจัดกลุ่มใหม่, LLM เสียเงิน หรือ Console ใหม่ในแผนนี้ เว้นแต่ผู้ใช้เปลี่ยนขอบเขตอย่างชัดเจน
8. ทำ Web เท่านั้น; ตรวจ Desktop 1440 และ 1000 px พร้อมความสูงที่ใช้งานจริง การย่อหน้าต่างเว็บไม่ใช่การกลับไปทำ Mobile app
9. เพิ่ม Tests ตามจุดเสี่ยง ตรวจ Browser เมื่อแก้ UI; build ใหม่ก่อนตรวจจริง ห้ามนำ fixture/mock มารายงานว่าเป็นผล real API/ASR หรือผลมนุษย์ประเมิน
10. ผลเก่า/หลักฐาน/แผนและเวอร์ชันต้องคงเดิม เมื่อเปิดผลเก่าไม่ประมวลผลทับเงียบ ๆ; success ต้องเกิดหลังบันทึกสำเร็จจริง
11. อย่าสร้างหน้าตั้งค่าที่ Backend ไม่ใช้ อย่าเพิ่มกราฟเพียงเพราะมีตัวเลข และอย่ารวมอันดับข้ามแพลตฟอร์ม/ขอบเขตอันดับ
12. ประกาศก่อนเปลี่ยนข้อมูลจริง/Train/Activate; ใช้ workflow ที่มี authorization/validation/rollback และยืนยันกับผู้ใช้ก่อนเปลี่ยน Active Model จริง ห้ามแก้ DB ตรงข้ามการตรวจรับของระบบ
13. บันทึกคำสั่ง ผลทดสอบ ภาพ และข้อที่ยังตรวจไม่ได้ทุกครั้ง ไม่ใช้จำนวน unit tests เป็นตัวแทนจำนวนคลิปหรือคุณภาพ AI
14. รายงานเดิมระบุ `.git` ของ worktree ชี้หาปลายทางไม่พบ ตรวจใหม่ก่อนใช้ Git; ถ้ายังเสียห้าม `git init`/แก้ pointer/ล้างงานเอง ใช้สำรองและ manifest ของไฟล์เป็นทางเลือกที่ระบุข้อจำกัด

## เวลาที่ควรกันไว้

- **พฤหัส 1 ต.ค. ช่วงแรก:** Phase 1 และเริ่ม Phase 2 โดยผู้ใช้เตรียมข้อมูลไปพร้อมกัน
- **พฤหัสช่วงที่เหลือ:** เน้นแก้ Analysis; Phase 3 ทำได้ระหว่างรอข้อมูลเมื่อผู้ใช้มอบหมายแยก
- **ศุกร์ 2 ต.ค. ช่วงเช้า:** ปิดข้อผิดพลาดหลักและหยุดเพิ่มฟีเจอร์ใหม่
- **ศุกร์ช่วงบ่าย:** กันเวลาให้ Phase 4 โดยเฉพาะ แล้ว Phase 5-6 ช่วงท้ายวัน อย่าให้การทดลองโมเดลกินเวลานี้ทั้งหมด
- **เสาร์-อาทิตย์:** อธิบายระบบและซ้อมจากรุ่นที่ freeze แล้ว ไม่สร้างฟีเจอร์เพิ่ม

ถ้าถึงวันพฤหัสช่วงบ่ายแล้วยังไม่มีข้อมูล/โมเดลที่ผ่านเกณฑ์ ให้แจ้งความเสี่ยงกำหนดส่งทันที ทำ UI/เอกสาร/flow ที่ไม่ติดก่อน และให้ผู้ใช้ตัดสินใจกับอาจารย์เรื่องส่งเป็นรุ่นที่มีข้อจำกัด ห้ามเรียก Analysis ว่าเสร็จหรือเปิดคำแนะนำที่ไม่ผ่านเกณฑ์เพื่อรักษากำหนดส่ง

## สิ่งที่ต้องการจากผู้ใช้

- ยืนยันการปรับข้อความขอบเขตใน Phase 1 โดยเฉพาะ Classification ไม่ใช่ Clustering และ YouTube/Google ไม่ใช่ TikTok
- Baseline ขาด Camera 6, Unknown Validation 10, Unknown Test 30 ตามเกณฑ์เปิดใช้ปัจจุบัน ให้ Phase 1 ตรวจจำนวนจริงและช่องที่เหมาะสมก่อนนำเข้า ไม่ย้ายคลิปที่รู้ผลแล้วไปเป็น Test
- Unknown หมายถึงอยู่นอก Phone/Camera/Laptop เช่น หูฟัง เมาส์ คีย์บอร์ดและอุปกรณ์เสริม เก็บหลายช่องและกรณีสับสนง่าย ไม่ให้ AI สร้าง transcript สมมุติเพื่อเติมจำนวน
- เตรียมคลิปอัปโหลดใหม่และฉบับแก้ไขจริงสำหรับตรวจ flow; หากจะอ้างความแม่น/ประโยชน์กับผู้ใช้ต้องมีชุดทดสอบ/ผู้ประเมินตาม protocol แยกต่างหาก

## Handoff มาตรฐาน

แต่ละ Phase สร้าง `docs/implementation/project-closeout-phase-N-handoff.md` ระบุ:

- สถานะ: ผ่าน / ผ่านเฉพาะส่วนที่ระบุ / รอข้อมูลหรือการตัดสินใจ / ไม่ผ่าน
- ขอบเขตที่ทำจริง, สิ่งที่ไม่ทำ, ข้อที่ยังไม่ได้รับอนุมัติ
- ไฟล์/endpoint/table ที่เปลี่ยน และ migration/rollback ถ้ามี
- เกณฑ์ผ่านทีละข้อกับหลักฐานจริง แยก fixture / live / human review
- คำสั่ง/ผล Tests, artifact paths, รุ่น/Model IDs/config ที่ใช้
- ข้อมูลและบัญชีทดสอบที่สร้าง/คืนค่า/เก็บไว้ ห้ามแนบ secret
- งานค้าง ผู้รับผิดชอบและ dependency ที่ขวาง Phase ต่อไป
- ขั้นตอนตรวจต่อสั้น ๆ สำหรับ agent ถัดไป และ URL ที่เปิดใช้งานได้

Handoff ต้องยังแสดงงานค้างแม้กำลังหมดเวลา ไม่เปลี่ยนสถานะเป็นผ่านเพียงเพื่อจบ Phase
