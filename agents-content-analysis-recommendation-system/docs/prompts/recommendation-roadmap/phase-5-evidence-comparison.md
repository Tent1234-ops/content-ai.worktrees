# Implementation Prompt: Recommendation Phase 5

## งานของคุณ

พัฒนา **เพิ่มน้ำหนักหลักฐานให้คำแนะนำ** ในโครงการ Content AI ให้ครบ Backend, การบันทึก, UI หลักฐาน และ Tests ทำเฉพาะ Phase นี้ ไม่เริ่มระบบอัปโหลดฉบับแก้ไขหรือการทดลองกับผู้ใช้

เป้าหมาย: จาก "พบหัวข้อนี้ในคลิปอ้างอิงผลตอบรับสูง" ไปสู่การเปรียบเทียบคลิปที่ตรวจพบ/ยังไม่ตรวจพบหัวข้อ ภายในกลุ่มที่พอเปรียบเทียบกันได้ ไม่ใช่พิสูจน์ว่าการพูดหัวข้อนั้นทำให้ยอดเพิ่ม

อ่านโค้ดจริงก่อน ทำ audit สั้น ๆ แล้วลงมือพัฒนา ไม่หยุดที่เสนอแผน หากข้อมูลจริงไม่พอ ให้ทำระบบงดสรุปและรายงานสิ่งที่ขาด ห้ามสร้างข้อมูลมาชดเชย

## ข้อห้ามที่ต้องรักษา

1. Active Model และผลตรวจรับหมวดยังเป็นผู้ตัดสินหมวดเพียงจุดเดียว Unknown/ถอดเสียงตรวจไม่ได้ ต้องไม่รับคำแนะนำเฉพาะหมวด
2. ไม่เปลี่ยน Threshold ของ Classification ไม่ Train/Activate โมเดล ไม่จำกัดความยาว Train Data ตามเพดานอัปโหลดผู้ใช้
3. ไม่ใช้ชื่อไฟล์ ชื่อคลิป คำอธิบาย หรือ Trend เป็นหลักฐานว่าพูดหัวข้อใน Transcript แล้ว
4. ไม่ใช้ Validation/Test เป็นคลิปอ้างอิง รวมถึงรายการที่ติดข้อห้ามเรื่องช่อง/คลิป/Transcript ซ้ำตามเกณฑ์เดิม
5. ไม่แก้ผลเก่าหรือ Fingerprint ของคำแนะนำที่บันทึกแล้ว การอัปเดตสถิติมีผลต่อการวิเคราะห์ใหม่เท่านั้น
6. ไม่เลือกเฉพาะผลบวก ไม่จัดอันดับคำแนะนำด้วย "เปอร์เซ็นต์เพิ่มยอด" และไม่เรียกความสัมพันธ์ว่าเป็นเหตุเป็นผล
7. ไม่เพิ่ม Paid API, LLM, Scraping หรือการเก็บข้อมูลภายนอกในงานนี้ ใช้ประวัติสถิติและรอบเก็บเดิม

## 1. Audit ข้อมูลก่อนคำนวณ

แยกกลุ่มข้อมูลสองบทบาทอย่างชัดเจน:

- `support cohort`: กลุ่มผลตอบรับสูงเดิมสำหรับข้อเท็จจริงว่าเคยพบหัวข้อในคลิปอ้างอิง
- `comparison cohort`: คลิปอ้างอิงที่ผ่านเกณฑ์ทั้งหมดในหมวดเดียวกัน ก่อนกรอง `_high_performing_rows` ต้องรวมคลิปทั่วไปด้วย

ปัจจุบัน `_documents()` ใน `actionable_recommendations.py` จำกัดตาม `dataset_profile.dataset_row_ids` ซึ่งเป็นกลุ่มผลตอบรับสูง ห้ามนำกลุ่มนี้มาแบ่งสองฝั่งแล้วอ้างว่าเทียบกับคลิปทั่วไป

นับเป็น Video ID ไม่ใช่จำนวนแถวหรือจำนวน Snapshot ไม่ซ้ำคลิปเดียวหลายครั้ง ไม่มี Channel ID/วันเผยแพร่/เวลาเก็บสถิติ/ที่มาที่ตรวจได้ให้รายงานเหตุผลที่ตัดออก ไม่เดาเติม

ใช้ `reference_transcript_rows` เป็นฐานโดยคงเกณฑ์ความปลอดภัยเดิม ไม่ลดเกณฑ์เพื่อให้ได้จำนวนมากขึ้น ตรวจข้อจำกัดว่าคลิปที่คัดด้วยมือไม่ใช่ตัวแทน YouTube ทั้งหมด ต่อให้มีทั้งคลิปทั่วไปและคลิปดังแล้วก็ตาม

ผล Audit ต้องแสดงจำนวนก่อน/หลังคัด แยกหมวดและช่อง เหตุผลที่ตัด จำนวนช่องที่มีคลิปได้ทั้งสองฝั่ง และรายการ Metadata ที่ขาด ต่อ UI คุณภาพ Dataset เดิมเท่าที่จำเป็น ไม่สร้าง Admin Console ใหม่

หากไม่มีฐานข้อมูลจริงที่เข้าถึงได้ ให้แสดงว่า audit ไม่ได้ ห้ามแต่งจำนวน ข้อมูลทั่วไปที่ยังไม่มีให้จัดทำรายการแนะนำการเก็บเพิ่ม ไม่ Auto-import

## 2. นิยามการตรวจหัวข้อ

- ใช้ Canonical topic, คำพ้อง และกติกาตรวจเดียวกับ Phase 2/3 ทั้งสองฝั่ง เก็บเวอร์ชันและ Hash
- ฝั่ง A: Transcript ตรวจพบหัวข้อ พร้อมข้อความจริงและตำแหน่งข้อความ
- ฝั่ง B: Transcript ทั้งคลิปตรวจได้ แต่ยังไม่ตรวจพบหัวข้อตามวิธีนี้ ไม่ใช่ยืนยันว่าคนไม่เคยพูด
- `unassessable`: Transcript ไม่ครบ คุณภาพ/ขอบเขตไม่พอ หรือไม่มีข้อความ ห้ามนับเป็นฝั่ง B
- ข้อความปฏิเสธ เช่น "ไม่มีชาร์จไร้สาย" นับว่ากล่าวถึงหัวข้อแล้ว ไม่แปลว่ามีฟังก์ชันนั้น
- Timestamp มีเฉพาะเมื่อมีหลักฐานเวลาจริง ไม่มีให้ใช้ Quote/Offset และแสดงว่าไม่มีเวลา
- ตรวจทุกหัวข้อใน Catalog ก่อนเลือกแสดงไม่เกิน 3 คำแนะนำ ไม่จำกัดการตรวจเหลือเฉพาะคำที่จะแสดง

## 3. Comparison Policy รุ่นแรก

ทำ Policy กลางที่ Version และ Hash ได้ พร้อม Unit tests ค่าต่อไปนี้เป็น **ค่าเริ่มต้นของโครงการ ไม่ใช่เกณฑ์รับรองนัยสำคัญ** กำหนดก่อนดูผลและห้ามลดอัตโนมัติเมื่อข้อมูลไม่พอ

| ค่า | ค่าเริ่มต้น |
| --- | --- |
| วันอ้างอิง | `as_of` ที่จับครั้งเดียวตอนสร้างผลใหม่ ใช้ UTC |
| สถิติสะสม | เลือก Observation ล่าสุดที่สำเร็จของแต่ละคลิป ไม่เกิน as_of และอยู่ใน 24 ชั่วโมงก่อน as_of |
| Metric version | เปรียบเทียบเฉพาะชนิดยอดวิวที่เข้ากันได้ ใช้ตัวตรวจเดิม Unknown version ให้ตัดออก |
| อายุคลิป ณ เก็บสถิติ | ช่วงวัน `[0,7)`, `[7,30)`, `[30,90)`, `[90,365)`, `[365,+inf)` |
| ความยาว | `(0,180]` และ `>180` วินาที เรียกว่า "กลุ่มความยาว" ไม่ยืนยันว่าเป็น YouTube Shorts |
| จำนวนเพื่อแสดงการเปรียบเทียบเชิงพรรณนา | อย่างน้อย 10 คลิปต่อฝั่งจากกลุ่มที่จับคู่ได้ และอย่างน้อย 5 ช่องที่มีทั้งสองฝั่ง |
| จำนวนเพื่อประมาณช่วงความไม่แน่นอน | อย่างน้อย 10 ช่องที่มีทั้งสองฝั่ง โดยยังผ่านเกณฑ์จำนวนคลิป |
| Bootstrap | 2,000 รอบ, seed คงที่ใน Policy, ช่วง 95%, สุ่มระดับช่อง |

หากมี Metadata รูปแบบ Shorts/วิดีโอทั่วไปที่ยืนยันที่มาได้ ให้แยกรูปแบบนั้นเพิ่มในกลุ่มเปรียบเทียบ ค่า unknown ต้องไม่ถูกรวมกับ confirmed format ห้ามอนุมาน Shorts จากความยาวอย่างเดียว

ใช้ `reference_video_statistics` เป็นแหล่ง Observation หลัก หากมีแต่ค่าล่าสุดใน `dataset_contents` ให้ใช้สำหรับแสดงหลักฐานเดิมได้ แต่ยังไม่ปั้นเป็น Observation ย้อนหลังเพื่อให้ผ่านการเปรียบเทียบ

ยอดไลก์/คอมเมนต์ที่ API ไม่ส่งมาเป็น `null` ไม่ใช่ 0 ตรวจความเสี่ยงที่คอลัมน์ Dataset เดิมมี default 0 อย่านำ default มาอ้างว่าเป็นค่าที่วัดได้

ไม่จับคู่ข้ามหมวด ข้ามกลุ่มความยาว/รูปแบบ ข้ามช่วงอายุ หรือข้าม Metric version เพื่อให้ครบจำนวน วันอ้างอิงของยอดต้องเป็นเวลาเก็บจริง ไม่ใช่วันเปิดหน้าเว็บ

## 4. วิธีคำนวณที่ต้องทำตาม

ประเมินแยก Metric ห้ามผสมเป็น Engagement Score ลึกลับ:

1. ยอดวิวสะสม ณ เวลาที่เก็บ เป็น Metric หลักที่กำหนดไว้ล่วงหน้า ไม่ใช่ความเร็วโต
2. ไลก์ต่อ 1,000 วิว = `likes / views * 1000`
3. คอมเมนต์ต่อ 1,000 วิว = `comments / views * 1000`
4. ยอดวิวเพิ่มเฉลี่ยต่อชั่วโมง ใช้ได้ตามเงื่อนไขข้อ 5

ถ้า views เป็น 0/null อัตราส่วนเป็น null พร้อมเหตุผล ถ้า likes/comments เป็น null ตัดเฉพาะ Metric นั้นและแสดงตัวหารจำนวนตัวอย่างใหม่ ไม่ทิ้งคลิปออกจากทุก Metric โดยไม่มีเหตุผล

ใช้การเทียบภายในช่องเพื่อลดความต่างของช่อง ไม่อ้างว่ากำจัดตัวแปรกวนได้หมด:

```text
กลุ่มย่อย = หมวด + รูปแบบที่ยืนยัน/unknown + กลุ่มความยาว + ช่วงอายุ + Metric version
ภายในแต่ละ (ช่อง, กลุ่มย่อย) ต้องมีทั้ง A และ B ที่ Metric ใช้ได้
กลาง_A_ช่องกลุ่ม = median ของ Metric ใน A
กลาง_B_ช่องกลุ่ม = median ของ Metric ใน B
ต่าง_ช่องกลุ่ม = กลาง_A_ช่องกลุ่ม - กลาง_B_ช่องกลุ่ม
ต่าง_ช่อง = median ของ ต่าง_ช่องกลุ่ม ภายในช่องนั้น
ผลต่างหลัก = median ของ ต่าง_ช่อง จากทุกช่องที่ใช้ได้
```

แต่ละช่องมีน้ำหนักเท่ากันในผลต่างหลัก ไม่ให้อีกช่องที่มี 50 คลิปกลบช่องที่มี 2 คลิป กลุ่มที่มีเพียงฝั่งเดียวใช้แสดงหลักฐานการพบได้แต่ไม่เข้าผลต่าง

แสดง Median, P25/P75 และจำนวนคลิปของแต่ละฝั่ง รวมจำนวนช่องและผลต่างหลักข้างต้น ระบุว่า Median ของสองฝั่งแบบรวมใช้บรรยายกลุ่ม ส่วน "ผลต่างภายในช่อง" เป็นคนละการคำนวณ ห้ามสลับชื่อหรือคาดว่าจะลบกันแล้วเท่ากันเสมอ

ช่วงความไม่แน่นอน: ใช้ Bootstrap กับรายการ `ต่าง_ช่อง` จึงสุ่มช่อง ไม่สุ่มแต่ละคลิปหรือ Snapshot เป็นตัวอย่างอิสระ ใช้ SciPy ที่ติดตั้งอยู่ด้วยวิธี BCa เมื่อรองรับและระบุเวอร์ชัน ห้ามอัปเกรดทั้ง Environment โดยไม่จำเป็น
ข้อมูล Degenerate, NaN หรือช่องน้อยเกินให้คืน `uncertainty_unavailable` และเหตุผล ไม่สร้างช่วง `[0,0]` หรือเปลี่ยนวิธีเงียบ ๆ

ช่วงนี้เป็นการประมาณความไม่แน่นอนภายในตัวอย่างที่เลือก ไม่แก้ Selection bias และไม่ใช่ความน่าจะเป็นที่คำแนะนำจะทำให้คลิปดัง ไม่เรียกผลหลายหัวข้อที่ลองพร้อมกันว่า "พิสูจน์นัยสำคัญ" หรือเพิ่ม P-value ใน Phase นี้

## 5. การเติบโตต้องใช้สองเวลาจริง

- ใช้ประวัติและกติกาใน `video_statistics_history` เป็นฐาน ไม่เขียนอีกสูตรที่ละเลย Failure/Metric change
- รุ่นแรกเลือก Observation ปลายล่าสุดใน 24 ชั่วโมงก่อน as_of และเลือกคู่ก่อนหน้าที่ใกล้ 24 ชั่วโมงก่อนปลายที่สุด ภายในช่วงห่าง 12-36 ชั่วโมง ถ้าเสมอเลือก Observation ID ตามกติกาคงที่
- ทั้งสองต้องเป็นคลิปเดียวกัน มีตัวเลขจริง เวลาเพิ่มขึ้น และ Metric เข้ากันได้ ไม่กระโดดข้าม Failed observation หรือ Counter correction ที่ทำให้ช่วงใช้ไม่ได้
- `จำนวนวิวเพิ่ม = วิวปลาย - วิวต้น`; `เฉลี่ยต่อชั่วโมง = จำนวนวิวเพิ่ม / ชั่วโมงที่ผ่านจริง`
- ติดลบให้เก็บเหตุการณ์แก้ยอดและงดอัตราโต ไม่ Clip เป็น 0 หากยอดไม่เปลี่ยนจริงสองเวลา จึงแสดง 0 ได้
- แสดงทั้งเวลาต้น/ปลายและจำนวนชั่วโมง เป็นค่าเฉลี่ยของช่วง ไม่ใช่ความเร็วทุกชั่วโมง และไม่ใช้ `average_views_per_day` จากยอดสะสมแทน
- ตรวจเกณฑ์จำนวนตัวอย่าง/ช่องใหม่สำหรับ Metric การเติบโต พร้อมรายงานช่วงเวลาที่แต่ละคลิปครอบคลุม

## 6. สถานะและข้อความที่ผู้ใช้เห็น

- `reference_only`: หลักฐานพบหัวข้อมี แต่ยังเทียบไม่ได้ ใช้ "พบในคลิปอ้างอิง" พร้อมจำนวน/ที่มา ไม่กล่าวว่าฝั่งหนึ่งดีกว่า
- `comparison_descriptive`: จำนวนผ่าน 10/ฝั่งและ 5 ช่อง แสดงค่ากลางและผลต่างที่สังเกตได้ พร้อม "ยังประเมินความไม่แน่นอนได้ไม่เพียงพอ" ไม่ฟันธงแนวโน้ม
- `comparison_uncertain`: คำนวณช่วงได้แต่คร่อม 0 ใช้ "ยังสรุปทิศทางความแตกต่างไม่ได้"
- `comparison_supported`: ช่วงคำนวณได้และไม่คร่อม 0 มี direction สูงกว่า/ต่ำกว่าในตัวอย่างนี้ ไม่ใช่ประโยชน์ที่รับประกัน
- `not_comparable`: ชนิดข้อมูล/เวลา/วิธีไม่เข้ากัน ระบุเหตุผล ไม่แปลงเป็นค่าศูนย์

ต้องแสดงผลต่ำกว่าและยังสรุปไม่ได้ในหลักฐานด้วย ไม่ซ่อนเพราะไม่สนับสนุนคำแนะนำ ถ้าคำแนะนำยังเกี่ยวข้องในเชิงเนื้อหาแต่หลักฐานไม่ได้สูงกว่า ให้บอกว่าเป็นทางเลือกเติมเนื้อหา ไม่ใช่คำแนะนำเพิ่มยอด

สถานะ จำนวนตัวอย่าง Direction และช่วงความไม่แน่นอนต้องแยกต่อ Metric เช่น ยอดวิวเทียบได้แต่คอมเมนต์เทียบไม่ได้ ห้ามเลือกแสดงเฉพาะ Metric ที่เป็นบวกแล้วสรุปรวมว่า "Engagement สูงกว่า" และห้ามใช้ P25/P75 แทนช่วงความไม่แน่นอนของผลต่าง

คงการเลือกข้อเสนอจากความเกี่ยวข้องและหลักฐาน Phase 3 เป็นหลัก ไม่ใช้ขนาดผลบวกมาเลือกเฉพาะหัวข้อที่ดูดี เกณฑ์ 2 คลิป/2 ช่องเดิมพอสำหรับการกล่าวว่า "พบ" แต่ไม่ใช่เกณฑ์สำหรับการสรุปเปรียบเทียบ

## 7. Data Contract และการบันทึก

เพิ่ม Contract แบบมี schema_version เช่น `evidence_bundle.topic_comparisons` ผูกด้วย `evidence_topic_id` เลือกชื่อให้เข้ากับโค้ดจริงและบันทึกไว้ในเอกสาร ห้ามเปลี่ยนความหมาย Field เดิมเงียบ ๆ

แต่ละหัวข้อต้องมี: method/policy/alias version และ Hash, as_of, cohort criteria, จำนวนก่อน/หลังและเหตุผลคัดออก, สองกลุ่มพร้อม Video/Channel/Dataset IDs, Observation IDs/Run IDs, วันเผยแพร่/เวลาเก็บ/ค่า Metric ที่ใช้, ข้อความรองรับการตรวจหัวข้อ, จำนวนช่องร่วม, ผลย่อยต่อช่อง, ผลรวม, ความไม่แน่นอน/เหตุผลที่ไม่มี และ limitation

เก็บข้อมูลที่พอคำนวณซ้ำพร้อมผลใหม่ใน Snapshot เดิม หรือจัดเก็บแบบ immutable ที่อ้างด้วย Hash ถ้าขนาดจำเป็น ห้ามบันทึกเพียง Dataset ID แล้วไปอ่านยอดล่าสุดตอนเปิดผลเก่า ห้ามบังคับว่าต้องสร้างตารางใหม่เมื่อโครงสร้างเดิมรองรับ

Fingerprint ต้องรวม Policy และข้อมูลที่ใช้จริง การแก้ยอด/Transcript/Dataset ภายหลังต้องไม่เปลี่ยนผลเดิมหรือทำให้แผน Phase 4 เปิดไม่ได้ หลักฐานจาก Trend ยังแยกจาก Transcript

คำนวณในงานวิเคราะห์ ไม่ใช่ GET หน้าผล มี Batch query และ Cache ตาม Data+Policy fingerprint หากจำเป็น ไม่สร้าง N+1 query ทุกหัวข้อทุกคลิป

UI เพิ่มในส่วนเปิดดูหลักฐานเดิม: สองกลุ่ม, หน่วย, ช่วงเวลา, จำนวนคลิป/ช่อง, ผลต่างและข้อจำกัด มี Loading/Error/Empty ชัดเจน ไม่สร้าง Dashboard ใหม่หรือใส่ตารางยาวในส่วนคำแนะนำหลัก

## 8. Tests และเกณฑ์ตรวจรับ

เพิ่ม Unit/Integration/Flutter tests โดยใช้ Fixtures ที่ระบุว่าจำลอง ไม่เขียนลงฐานจริง:

- ไม่ใช้เฉพาะกลุ่มผลตอบรับสูง และไม่ให้ Holdout/ช่องซ้ำ/Deleted dataset หลุดเข้า
- คำพ้อง/ข้อความปฏิเสธนับถูก Transcript ไม่ครบไม่เข้าฝั่ง B Quote/Offset ตรงจริง ไม่มี Timestamp ปลอม
- คลิปซ้ำหลาย Observation ยังเป็นหนึ่งตัวอย่าง ช่องตัวอย่างมากไม่ครอบงำผลรวม
- ทดสอบทุกขอบช่วงอายุ/ความยาว/เวลา, null/0, Metric version ไม่เข้ากัน, เวลาอนาคตและอายุคลิปติดลบ
- Fixture คำนวณ Median/อัตราต่อพัน/ผลต่างระดับช่องด้วยมือได้ ผลบวก ลบ เสมอ และกลุ่มที่ไม่มีคู่
- Bootstrap seed ทำซ้ำได้, ช่องน้อย, ค่าคงที่/NaN, ช่วงคร่อม 0, ไม่มีการสรุปเปอร์เซ็นต์รับประกันยอด
- การโตมีสองเวลาจริง ตัวอย่าง 1,000 -> 1,600 ใน 24 ชั่วโมงได้ 25 วิว/ชั่วโมง; ข้อมูลครั้งเดียว/Failure/ยอดลดต้องไม่ปลอมเป็น 0
- ผลเก่าและแผนเดิมไม่เปลี่ยนหลังแก้ Dataset/Policy เปิดผลแล้วไม่เรียก YouTube หรือคำนวณใหม่
- UI แสดงหลักฐานทั้งทิศบวกและลบ ข้อมูลไม่พอ และอ่านได้บนเว็บที่ความกว้าง 1,000/1,440 พิกเซล ไม่ต้องทำแอป Mobile

รัน Regression อย่างน้อย `test_actionable_recommendations.py`, `test_recommendation_evidence.py`, `test_reference_statistics.py`, `test_dataset_readiness.py`, `test_clip_revision_plans.py` และ Tests ใหม่ พร้อม Flutter analyze/tests ที่กระทบ ตรวจ Browser จริงด้วยข้อมูลแยกฐานและบันทึก Screenshot

## 9. ส่งมอบ

ทำโค้ดและ Tests ให้ครบ แล้วสร้าง `docs/implementation/recommendation-phase5-handoff.md` ระบุ Contract/ไฟล์/สูตร/Policy/คำสั่งทดสอบ/ข้อจำกัด/งานที่ Phase 6 ต้องรู้

สรุปสองบรรทัดสถานะแยกกัน: "ฟีเจอร์และการทดสอบซอฟต์แวร์" กับ "ความพร้อมของหลักฐานจริง" ถ้าข้อมูลจริงเทียบไม่ได้ นั่นไม่ใช่เหตุให้ปลอมผลหรือบอกว่าได้พิสูจน์แล้ว ให้บอกว่าต้องเพิ่มข้อมูลชนิดใด

ถ้าต้องหยุดเพราะข้อจำกัด Session ให้บันทึกงานที่ทำแล้ว งานค้าง คำสั่ง Test ล่าสุด และข้อผิดพลาดจริงใน Handoff ห้ามเขียนว่าสำเร็จครบเพื่อปิดงาน และไม่ขยายไป Phase ถัดไปเอง

ไม่รัน Live collector หรือแก้ข้อมูลจริงเพื่อให้ Demo มีผล ใช้ Server ทดสอบแยกและหลีกเลี่ยง Startup ที่เรียก Trend API เมื่อทำ UI เสร็จให้ URL ที่เปิดทดสอบได้ ตรวจความสำเร็จจากการบันทึกจริง ไม่ใช่แค่ HTTP 200
