# Implementation Prompt: Recommendation Phase 7

## งานของคุณ

พัฒนาและใช้เครื่องมือ **ประเมินประโยชน์ของคำแนะนำ** เพื่อสร้างรายงานที่ตรวจสอบได้ แยก "จำแนกหมวดถูกไหม" ออกจาก "คำแนะนำเกี่ยวข้อง เข้าใจง่าย และนำไปทำต่อได้ไหม"

ทำเฉพาะ Phase นี้ ไม่ Train/Activate โมเดล ไม่แก้ Threshold/แม่แบบหลังดูผล Test และไม่นำคลิปทดสอบเข้า Dataset อ้างอิงเพื่อให้ผลดีขึ้น

ถ้ายังไม่มีคลิปใหม่หรือคะแนนคนจริง ให้ทำ Protocol, เครื่องมือ, แบบประเมิน และการตรวจความถูกต้องให้พร้อม แต่ระบุ `awaiting_fresh_clips` / `awaiting_human_ratings` ห้ามสร้างคะแนนแทนหรือประกาศว่าประเมินประโยชน์เสร็จแล้ว

## 1. แยกผลที่ประเมินเป็นสามส่วน

1. **Classification**: หมวดตรง Gold label หรือไม่ และปฏิเสธ Unknown ได้ไหม
2. **Evidence correctness**: Dataset/Quotes/ตัวเลข/เวอร์ชัน/ช่วงเวลา/กลุ่มเปรียบเทียบถูกต้องหรือไม่ ตรวจอัตโนมัติร่วมกับคนได้ แต่ไม่เท่ากับวัดประโยชน์
3. **Recommendation utility**: คนดูคลิปแล้วเข้าใจคำแนะนำ เห็นว่าเกี่ยวข้อง ไม่ซ้ำ และนำไปปรับได้หรือไม่ ต้องมีการประเมินจากคนจริง

ห้ามใช้ Classification confidence, จำนวนคำแนะนำ, จำนวนอ้างอิง หรือ Unit test ผ่าน แทนคะแนนความมีประโยชน์ และห้ามสรุปว่าจะเพิ่ม Engagement เพราะยังไม่มีการทดลองยอดหลังเผยแพร่

## 2. ชุดคลิปและการกันข้อมูลรั่ว

เริ่มต้นเป็น Pilot ที่ระบุขนาดชัด ไม่อ้างว่าเป็นจำนวนเพียงพอทางสถิติ:

| กลุ่ม | จำนวนตั้งต้น | ความหลากหลาย |
| --- | ---: | --- |
| Phone | 3 | รีวิวทั่วไป/เน้นกล้อง/เน้นเกม รวมคลิปถ่ายเองอย่างน้อย 1 |
| Camera | 3 | กล้องเฉพาะทาง/งานวิดีโอ/ประเด็นสับสนกับกล้องมือถือ รวมถ่ายเองอย่างน้อย 1 |
| Laptop | 3 | งานทั่วไป/เล่นเกม/ประเด็นสับสน รวมถ่ายเองอย่างน้อย 1 |
| Unknown | 3 | อุปกรณ์เสริมและอย่างน้อย 1 เรื่องนอกอุปกรณ์ไอที |

อย่างน้อย 12 คลิปไม่ซ้ำและ 3 ผู้ประเมิน แสดงจำนวนที่ได้จริง ถ้ายังไม่ครบให้รายงาน Pilot ไม่ครบ ไม่เลือกตัดหมวดที่ทำได้ไม่ดีทิ้ง ไม่สั่งให้ผู้ใช้ถ่ายคลิปโดยอ่านพจนานุกรมคำของระบบ

ก่อนรัน Prediction ต้องมี Manifest: case_id, file hash, แหล่งที่มา, Video/Channel/creator ID ถ้ามี, source_kind, Gold label, คนยืนยัน label/independence, วันลงทะเบียน, บทบาท heldout/regression และสถานะยินยอมใช้คลิป

กันซ้ำด้วย File hash, Video ID, Channel/creator ที่ใช้พัฒนา, Transcript exact/near-copy audit และกติกา Holdout เดิม Source identity ไม่พอให้ `independence_unconfirmed` ไม่อ้างว่า Hash ต่างแล้วเป็นคลิปใหม่แน่นอน

คลิปที่ใช้แก้บั๊ก หูฟัง/คีย์บอร์ด/เมาส์/Review_Phone หรือ Test 17 Transcript เก่าคือ Regression/Historical evidence ไม่ใช่ Test ใหม่ ตรวจประวัติจริง ไม่สมมุติว่าชื่อไฟล์ใหม่ทำให้เป็นคลิปใหม่

หากดูผลแล้วนำไปปรับระบบ ให้ทำเครื่องหมายชุดนั้นเป็น Development/Regression และหาชุดใหม่สำหรับ Final test ไม่ลบประวัติการใช้คลิป

ชุดทดสอบใหม่และข้อมูลผู้ประเมินแยกจากฐาน Production ไม่ Auto-import ไป Dataset ไม่ทำงานดึง YouTube/ถอดเสียง/ฝึกโมเดลจำนวนมากโดยไม่จำเป็น

## 3. ล็อกเงื่อนไขก่อนดูคะแนน

สร้าง Protocol JSON/Markdown มี Version, SHA-256, Created time และ Seed ก่อนรับคะแนนจริง ระบุ:

- รายการคลิป/เกณฑ์รวมและตัดออก จำนวนขั้นต่ำ บทบาท Pilot และแผนหยุดเก็บ
- Model artifact/Acceptance policy, ASR/settings, Topic/template/comparison versions
- Dataset/reference snapshot และ Statistics cutoff เดียวกันสำหรับทุก Variant
- Variant definitions, การจัดลำดับ, รูปแบบแบบประเมิน, Primary metrics และเกณฑ์ผ่าน
- วิธีจัดการงานล้มเหลว Empty advice, N/A, คะแนนขาด, Rater ซ้ำ และผลที่ไม่ตรง Hash
- ประเภทข้อผิดพลาดร้ายแรง เช่น แนะนำผิดหมวด, Quote แต่ง, ข้อมูล Test รั่ว, อ้างเหตุให้ยอดเพิ่ม

ถ้า Protocol เปลี่ยนหลังดูคะแนน ให้สร้าง Version ใหม่และรายงานว่าปรับหลังเห็นผล ไม่เขียน Hash ทับเพื่อให้ดูเหมือนกำหนดไว้ก่อน

## 4. เปรียบเทียบ 3 รูปแบบอย่างยุติธรรม

สำหรับคำถาม "รูปแบบคำแนะนำช่วยผู้ใช้ไหม" ใช้ผลวิเคราะห์เดียวกัน หัวข้อเดียวกัน ลำดับเดียวกัน จำนวนเท่ากันจาก Frozen snapshot แล้วสร้าง Presentation variants:

- A: รายการชื่อหัวข้อ/Keyword ภาษาไทยเท่านั้น
- B: หัวข้อเดียวกับ A + สิ่งที่พบ/สิ่งที่เสนอ/เงื่อนไข/วิธีทำ/ประโยคตัวอย่าง ไม่แสดงสถิติเปรียบเทียบหรือแหล่งอ้างอิง
- C: เนื้อหา B เหมือนกัน + เหตุผล หลักฐาน ที่มา จำนวนตัวอย่าง เวลา และสถานะ/ข้อจำกัด Phase 5 ตามจริง

ห้ามให้ C ได้หัวข้อใหม่ที่ A/B ไม่ได้ หรือเลือกเฉพาะเคสที่ C มีผลบวก บันทึกข้อจำกัดของ C ที่มีเพียง `reference_only` ด้วย

เรียก A ว่า **Baseline รูปแบบรายการ Keyword** ไม่อ้างว่าเป็นการ Replay โค้ดเก่าทั้งระบบ ถ้าต้องเทียบระบบเก่าจริง ให้ทำรายงานอีกส่วนชื่อ Historical pipeline comparison ใช้ Snapshot/Code version จริง และชี้ว่าหลายองค์ประกอบเปลี่ยนจึงแยกผลจากรูปแบบแสดงไม่ได้

สรุปคลิป/ความยาว/ข้อมูลพื้นฐานต้องเหมือนกันทุก Variant หรือซ่อนทั้งหมดสำหรับการทดลอง ไม่แสดง Classification confidence ให้ผู้ประเมินใช้แทนการตัดสินคำแนะนำ Current-trend ideas ที่ไม่อยู่ในโจทย์ให้ซ่อนเหมือนกันทั้งสาม

ไม่มีคำแนะนำต้องยังมีเคสในรายงาน ไม่ตัดเคสล้มเหลว/Unknown ออกเพื่อให้คะแนนดูดี แต่แยกฐานนับให้ตรงกับคำถามที่ประเมิน

## 5. การให้คนประเมิน

ทำ Review packet/CSV หรือหน้าเว็บประเมินขนาดเล็กที่ใช้ UI เดิมตามความเหมาะสม เลือกวิธีที่เก็บคะแนนได้จริงโดยไม่ต้องสร้างระบบบัญชีงานวิจัยใหม่

- ผู้ประเมินดูวิดีโอจริงก่อน และเขียนว่ามีจุดที่ควรเพิ่มเติมหรือไม่ก่อนเห็น Variant เพื่อไม่ให้ระบบเป็นผู้กำหนด Gold ของตัวเอง
- ใช้รหัสไม่บอกว่า "ใหม่/ดีกว่า" เก็บ Mapping ของ Variant แยกจากแบบฟอร์ม
- ใช้ลำดับทั้ง 6 แบบของ A/B/C กระจายใกล้เคียงกันตาม Seed ที่ล็อกไว้ สมดุลข้ามผู้ประเมินและคลิป ไม่ใช่แค่สุ่มครั้งเดียวทั้งโครงการ
- แสดงทีละรูปแบบ ให้ส่งคะแนนก่อนเห็นรูปแบบถัดไป ห้ามเติมคะแนนให้โดยอัตโนมัติ
- ผู้ประเมินอาจจำเนื้อหาจากรูปแบบก่อน จึงระบุ Carryover limitation; อย่าอ้างว่า Blinded สมบูรณ์เพราะ C มีหลักฐานให้เห็นอย่างชัดเจน
- ใช้รหัสผู้ประเมิน ไม่ต้องเก็บชื่อจริง/อีเมลที่ไม่จำเป็น เก็บ Consent และไม่เผยแพร่ Transcript/ไฟล์ที่ไม่มีสิทธิ์

Key คะแนนใหม่ต้องแยก `study_id + protocol_hash + case_id + output_hash + variant_id + reviewer_id + unit_id` ให้ชัดว่าเป็นคะแนนทั้งชุดคำแนะนำหรือรายข้อ ไม่ปนกัน
เก็บคะแนนทั้งชุดเป็นหน่วยหลักต่อคลิป/รูปแบบ/คน และใช้ข้อผิดพลาดรายข้อสำหรับ Audit เพิ่ม ไม่เอา 3 ข้อในคลิปเดียวมาอ้างว่าเป็น 3 คลิปอิสระ

## 6. Rubric และค่า N/A

เก็บคะแนน 1-5 โดย 5 = ดี กำหนดคำอธิบาย 2/4 เป็นระดับระหว่างตัวอย่าง 1/3/5 และให้เขียนเหตุผลเมื่อคะแนนต่ำ:

| มิติ | 1 | 3 | 5 |
| --- | --- | --- | --- |
| ความเกี่ยวข้อง | ผิดสินค้า/ผิดบริบท | เกี่ยวบางส่วน ยังทั่วไป | ตรงคลิปและเงื่อนไขสินค้า |
| ไม่ซ้ำสิ่งที่พูดแล้ว | ส่วนใหญ่พูดแล้ว | มีทั้งใหม่และซ้ำ | เป็นประเด็นเพิ่มที่ยังไม่พบจริง |
| ความเข้าใจง่าย | อ่านแล้วไม่รู้ความหมาย | เข้าใจแต่ต้องถามเพิ่ม | เข้าใจได้ด้วยตนเอง |
| นำไปทำต่อได้ | ไม่รู้ว่าจะปรับอะไร | รู้เรื่องที่จะเพิ่มแต่ขั้นตอนไม่ชัด | บอกได้ว่าจะปรับตรงไหนและทำอย่างไร |
| ความถูกต้องของหลักฐาน | แหล่ง/Quote/ตัวเลขผิด | ตรวจได้บางส่วน/มีข้อจำกัดไม่ชัด | ตรวจย้อนกลับได้และข้อสรุปไม่เกินข้อมูล |

มิติหลักฐานของ A/B ที่ไม่ได้แสดงแหล่งอ้างอิงเป็น N/A ไม่ใช่ 0 หรือ 5 เปรียบเทียบคุณภาพการอ้างอิงของ C กับเกณฑ์โดยตรง ไม่ทำกราฟที่ชี้ว่า C ชนะ A/B เพราะอีกสองไม่มีฟีเจอร์นี้

แยกคะแนน "เข้าใจเหตุผลที่ระบบแนะนำ" เพิ่มได้เป็น Secondary outcome หากกำหนดใน Protocol ตั้งแต่ต้น ไม่ใช้ความรู้สึกน่าเชื่อถือแทนตรวจว่าอ้างอิงถูก

คำแนะนำว่างต้องตรวจว่าเหมาะสมหรือไม่ Unknown ที่งดแนะนำถูกต้องไม่ควรได้คะแนนต่ำเพียงเพราะไม่มีคำแนะนำ หากคลิปที่คนระบุไว้ก่อนว่ามีจุดควรเพิ่มแต่ระบบงดผิด ให้บันทึก missed_opportunity ไม่ซ่อนจาก Coverage/รายงาน

หลักฐานเชิงสถิติไม่พอแต่ C บอกว่าไม่พออย่างถูกต้อง อาจได้คะแนนความถูกต้องสูงได้ ไม่บังคับว่าทุกคำแนะนำต้องมีผลเปรียบเทียบเป็นบวก

เพิ่ม Critical flags แยกจาก Likert: wrong_category, duplicated_topic, fabricated_quote_or_time, incorrect_count, unsupported_spec, causal_engagement_claim ให้ตรวจยืนยันกรณีที่มีคนรายงานก่อนสรุป

## 7. Metrics และเกณฑ์ตัดสินที่ล็อกล่วงหน้า

ค่าเริ่มต้นต่อไปนี้เป็น **เกณฑ์โครงการสำหรับ Pilot** ไม่ใช่ผล Power analysis หรือมาตรฐานสากล แสดงว่าเปลี่ยนได้ก่อนเริ่มเก็บคะแนน แต่ห้ามลดหลังเห็นผล

### Classification แยกรายงาน

- แสดง N ของแต่ละ Gold class, Confusion matrix, Accuracy, Macro F1, Precision/Recall/F1 รายหมวด และจำนวน Failures
- In-scope accuracy ให้นับ Phone/Camera/Laptop ที่ระบบทาย Unknown เป็นความผิดด้วย ไม่คิดเฉพาะคลิปที่ระบบยอมรับ
- Unknown rejection = จำนวน Gold Unknown ที่ระบบปฏิเสธ / Gold Unknown ทั้งหมด
- Unknown false acceptance = Gold Unknown ที่ยอมรับเป็นหมวดใดหมวดหนึ่ง / Gold Unknown ทั้งหมด
- แสดง Coverage/อัตรางดแนะนำและจำนวนงานถอดเสียง/วิเคราะห์ล้มเหลวแยก ไม่มี Gold หรือไม่มีตัวอย่างให้ null ไม่ใช่ 0%
- สำหรับ Pilot ตั้งเป้า In-scope accuracy >= 80%, Macro F1 สามหมวด >= 0.75 และไม่ยอมรับ Unknown ผิดในชุด Pilot ที่เก็บ รายงานตัวเศษ/ตัวส่วนเสมอ ไม่ตีความ 3/3 ว่าจะปฏิเสธได้ 100% ในโลกจริง
- งานล้มเหลวไม่ใช่การปฏิเสธ Unknown ที่ถูกต้อง ต้องเป็น Error ไม่ให้เพิ่มคะแนน Rejection; ระบุฐานนับผลสำเร็จและ End-to-end coverage คู่กัน

### Recommendation แยกรายงาน

- หน่วยสรุปหลักเป็นคลิป: รวมคะแนนคนภายในแต่ละ (คลิป, Variant) ก่อน แล้วรายงาน Median/P25/P75 ข้ามคลิป จำนวนคลิป/คน/คะแนนจริงครบ
- Primary comparison: คะแนนนำไปทำต่อได้ B-A แบบจับคู่คลิป เป้าหมาย Median ของผลต่าง >= 0.5 คะแนน
- C ต้องไม่ทำให้คะแนนนำไปทำต่อได้ต่ำกว่า B โดย Median ผลต่าง C-B >= 0 และความถูกต้องหลักฐานของ C มี Median >= 4
- C มี Median ความเกี่ยวข้อง/ไม่ซ้ำ/เข้าใจง่าย >= 4 และ Critical flags ที่ยืนยันแล้วเป็น 0
- ตั้งฐานนับ Primary utility เป็น In-scope clips ที่คนระบุว่ามีจุดควรเพิ่มก่อนดูผล ไม่มีคำแนะนำเพราะระบบพลาดยังอยู่ในการนับนี้ ส่วนเคสไม่มีจุดควรเพิ่มและ Unknown รายงานความเหมาะสมของการงดแนะนำแยก
- หาก Primary clips ที่มีคะแนนครบทั้ง A/B/C น้อยกว่า 6 หรือผู้ประเมินครบต่ำกว่า 3 ให้ `insufficient_utility_evaluation` ไม่ประกาศผ่าน แม้ตัวเลขสูง
- คะแนนที่ขาดไม่นับเป็น 0; ใช้ Complete pairs สำหรับผลต่าง และแสดงจำนวนที่ขาด/เหตุผล/ความต่างของ Coverage ไม่เลือก Pair ตามคะแนน

ฐาน Primary ที่ควรมีข้อเสนอแต่ได้รับคำแนะนำว่าง ให้คะแนนนำไปทำต่อได้ 1 ตาม Rubric พร้อม missed_opportunity ไม่ถือเป็นคะแนนที่คนยังไม่ได้กรอกและไม่ตัดออก; ต้องให้คนประเมินยืนยันว่าระบบพลาดจริงก่อน ส่วนงานวิเคราะห์ล้มเหลวรายงานแยกเป็น Failure พร้อมแสดงความครอบคลุม ห้ามปลอมว่าเป็น Variant ที่มีผลสำเร็จ

รายงาน Paired differences และจำนวนชนะ/เสมอ/แพ้ ไม่เอาคะแนนทุกคนทุกข้อเป็นตัวอย่างอิสระ ไม่เพิ่ม P-value หรืออ้างผลทั่วไปจาก Pilot ขนาดเล็ก ขนาดตัวอย่างและความแปรปรวนจริงต้องเห็นได้

ผลก่อน-หลังจาก Phase 6 ใช้เป็นกรณีศึกษาแยก: สิ่งที่เลือกปรับ -> ตรวจพบข้อความอะไร -> ยังไม่แน่ใจตรงไหน ไม่ใช้แทนการวัด Engagement หรือเพิ่มจำนวน Test ด้วย Revision ของคลิปเดิม

## 8. สิ่งที่เครื่องมือต้องสร้าง

ใช้ Output directory ใหม่เสมอ เช่น `artifacts/evaluation/recommendation-utility-<run-id>/` ภายใต้แนวทาง Artifacts เดิม ประกอบด้วย:

- Manifest และ Protocol ที่แช่แข็ง พร้อม Hash/Seed/Versions
- Overlap audit และเหตุผลรวม/ตัด Case ไม่ลบ Case ที่ผิดออกจากรายงานต้นฉบับ
- Per-case result และ Presentation A/B/C พร้อม Hash และต้นทาง Snapshot เดียวกัน
- Allocation ของลำดับผู้ประเมินที่ตรวจความสมดุลได้ ไม่เปิดเผย Mapping ใน Rater packet
- แบบประเมินว่างและไฟล์รับคะแนนที่ตรวจ Duplicate, stale hash, invalid score, N/A, ผู้ประเมิน/Case ไม่อยู่ในแผน
- `report.json`, รายงานภาษาไทย, ตาราง Classification/Utility/Evidence ที่แยกกัน และสถานะ pending เมื่อข้อมูลยังไม่ครบ
- สรุปสำหรับพรีเซนต์: วิธีทำ, ประโยชน์ที่วัดได้จริง, ตัวอย่างดี, ตัวอย่างล้มเหลว, ข้อจำกัด และสิ่งที่ยังไม่ได้พิสูจน์

เก็บรายละเอียด Source/Quote สำหรับ Audit ในพื้นที่ที่เหมาะสม ไม่ Export Secrets/Token/ข้อมูลส่วนตัว และไม่แจก Transcript เต็มที่ไม่มีสิทธิ์เพียงเพราะอยู่ใน Dataset

## 9. Verification

เพิ่ม Tests สำหรับ:

1. ชุดเก่า/Regression/Hash ซ้ำ/ช่องพัฒนาซ้ำไม่กลายเป็น fresh heldout เปลี่ยนชื่อไฟล์หลบไม่ได้
2. Protocol เปลี่ยน/Output hash เปลี่ยนแล้วไม่รับคะแนนเก่าอย่างเงียบ ๆ
3. A/B/C มีหัวข้อและลำดับเท่ากัน B/C มีเนื้อหาวิธีทำเหมือนกัน ไม่เพิ่มหัวข้อที่ C ได้เปรียบ
4. ลำดับ 6 แบบทำซ้ำตาม Seed ได้ และกระจายสมดุลตามจำนวนที่เป็นไปได้
5. หลายผู้ประเมินต่อ Case ไม่ถูกทิ้งว่า Duplicate; ส่งซ้ำจริงไม่ถูกนับเพิ่ม
6. คะแนนว่าง/N/A ไม่เป็น 0/5; Empty recommendation/Failed job/Unknown ยังคงอยู่และมีฐานนับถูกต้อง
7. Metric fixtures คำนวณด้วยมือได้: Confusion/Unknown/Coverage, คะแนนต่อคลิป, Paired difference, ชนะ/เสมอ/แพ้
8. รูปแบบคะแนน 0/1 เก่ายังอ่านด้วย Contract เก่า ไม่แปลงเป็น Likert เอง
9. ไม่มีคะแนนคนจริง -> Human utility เป็น not_evaluated ไม่สร้างรายงานผ่านจาก Fixture
10. Import/Export และรันซ้ำไม่แก้ Production dataset, Model, ผลเก่า หรือ Artifacts ก่อนหน้า

รัน Tests เดิมของ Analysis evaluation, Recommendation evidence, Actionable advice, Phase 5/6 ที่เกี่ยวข้อง ถ้ามีหน้า Review เพิ่มให้รัน Flutter tests และ Browser flow พร้อม Screenshot
ทดสอบ Software ด้วย Synthetic fixtures ได้ แต่ห้ามรวมในจำนวนคลิป/ผู้ประเมินจริง

## 10. เกณฑ์จบและส่งต่อ

แยกสถานะสองระดับ:

- `tooling_ready`: สร้าง Packet, รับคะแนน, Audit, คำนวณ, Export และ Tests ผ่าน
- `evaluation_complete`: มีคลิปใหม่/คะแนนจริงครบตาม Protocol และรายงานทั้งผ่าน/ไม่ผ่านอย่างตรงไปตรงมา ไม่จำเป็นว่าผลต้องดีเพื่อให้รายงานเสร็จ

เกณฑ์ว่าระบบได้ตามเป้าหมายของโครงการใช้ค่าที่ล็อกในข้อ 7 ถ้าไม่ผ่านให้บอกว่าไม่ผ่าน พร้อมแผนรอบถัดไป ไม่แก้กฎ/คำแนะนำแล้วรันชุดเดิมซ้ำโดยเรียกว่า Test ใหม่

สร้าง `docs/implementation/recommendation-phase7-handoff.md` ระบุคำสั่งจริงสำหรับเตรียมชุด/รัน/ส่งแบบประเมิน/รับคะแนน/ออกรายงาน พร้อมคำอธิบายภาษาไทยสำหรับตอบอาจารย์

หากขาดคลิปหรือคนประเมิน ให้จบด้วยจำนวนและชนิดข้อมูลที่ต้องขอเพิ่ม ไม่ยืมผล Accuracy เก่ามายืนยัน Phase นี้ และไม่สรุปว่าได้เพิ่มยอดวิวจริง

หากต้องหยุดระหว่างทำ ให้บันทึก Progress และงานค้างใน Handoff โดยไม่แก้สถานะ pending ให้ผ่าน และไม่สร้างผลผู้ประเมินจำลองลงในรายงานจริง

หลักป้องกันข้อมูลรั่วอ้างอิง [scikit-learn: Data leakage](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage) และการแยกกลุ่มอ้างอิง [Grouped data](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data) เอกสารเหล่านี้ไม่ได้รับรองขนาด Pilot หรือเกณฑ์คะแนนที่กำหนดในโครงการนี้
